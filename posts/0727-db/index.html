오늘 수업에서 꼭 가져가야 할 것

여러 사람이 함께 바꾸는 감자 식당 주문 데이터를, 왜 파일 한 장이 아니라 DBMS 안의 여러 테이블과 관계로 나눌까요?

오늘 꼭 가져갈 문장은 하나입니다. DBMS가 여러 테이블의 규칙을 관리하고, PK가 기록을 구별하며 FK가 떨어진 기록을 연결합니다. ERD·스키마·DDL·DML은 아래 코드에서 역할만 먼저 알아봅니다.

데이터베이스와 DBMS는 다릅니다

데이터베이스(Database)는 관련 있는 데이터를 일정한 구조로 모아 둔 저장 공간입니다.

DBMS(Database Management System)는 데이터베이스를 만들고 읽고 바꾸는 일을 관리하는 소프트웨어입니다. PostgreSQL은 DBMS이고, 그 안에 감자 식당 데이터베이스를 만들 수 있습니다.

감자 식당으로 비유하면 데이터베이스는 고객·메뉴·주문 장부를 모아 둔 주문 장부실이고, DBMS는 장부를 읽고 바꾸는 요청과 규칙을 관리하는 시스템입니다. 장부 더미가 스스로 일하진 않습니다. 실제 DBMS는 사람이 아니라 소프트웨어입니다.

여러 사람이 같은 데이터를 다룰 때 DBMS는 조회와 변경, 데이터 규칙과 작업 취소 같은 기능을 제공합니다. 그렇다고 올바른 테이블 구조까지 자동으로 설계해 주는 것은 아닙니다.

ACID

트랜잭션이 안전하게 동작하기 위한 네 가지 성질의 묶음.

트랜잭션과 ACID의 세부 원리는 나중에 다룹니다. 오늘은 여러 변경을 한 작업으로 관리한다는 역할만 알아두면 됩니다.

관계형 데이터베이스는 행과 열이 있는 테이블을 사용합니다

관계형 DBMS(RDBMS)는 데이터를 테이블로 나누고, 관련된 기록을 키로 연결해 관리하는 DBMS입니다.

  • 테이블: 같은 종류의 기록을 모아 둔 구조
  • 행(row): 고객 한 명, 주문 한 건처럼 저장된 기록 하나
  • 열(column): 고객명, 메뉴명, 수량처럼 모든 행에서 같은 의미를 가진 항목

감자 식당이라면 고객 장부, 메뉴 장부, 주문 장부를 각각 테이블로 나눌 수 있습니다.

PK는 구별하고 FK는 연결합니다

PK(Primary Key, 기본 키)는 한 테이블에서 각 행을 유일하게 구별합니다. 감자 식당에서는 고객과 주문마다 겹치지 않는 번호표를 붙여, 같은 이름이나 내용이 있어도 어느 행인지 찾게 합니다.

FK(Foreign Key, 외래 키)는 다른 테이블의 키를 가리킵니다. 주문 장부의 고객 번호가 고객 장부의 번호표를 가리키게 해, 떨어진 두 장부를 연결합니다.

관계의 숫자는 두 종류의 기록이 몇 대 몇으로 이어지는지 나타냅니다.

  • 1:1: 고객 한 명과 고객 카드 한 장처럼 양쪽에 하나씩 연결
  • 1:N: 고객 한 명이 여러 주문을 남기는 연결
  • N:M: 여러 고객이 여러 메뉴를 주문하는 연결

N:M 관계는 보통 두 테이블을 바로 붙이지 않고 주문 같은 중간 테이블을 두어 표현합니다.

수업에서 설계 용어가 보이면: ERD → 스키마 → SQL

데이터 모델링은 현실의 요구사항을 저장할 구조로 바꾸는 설계 과정입니다.

ERD(Entity Relationship Diagram)는 그 구조를 미리 그린 설계도입니다.

  • 엔티티: 고객·메뉴·주문처럼 데이터로 관리할 대상
  • 속성: 고객명·가격·수량처럼 대상에 관해 저장할 항목
  • 관계: 고객과 주문처럼 기록들이 연결되는 규칙

수업에서는 개념적 모델, 논리적 모델, 물리적 모델이라는 이름도 나옵니다. 지금은 현실의 요구사항을 실제 DB 구조로 차례대로 구체화한다고만 보면 됩니다.

PostgreSQL의 스키마(schema)는 관련 테이블을 한 이름 아래 묶는 논리적 구역입니다. 감자 식당에서 쓰는 테이블들을 potato_shop이라는 구역에 모을 수 있습니다.

정규화

중복과 변경 오류를 줄이도록 테이블 구조를 나누는 설계 과정.

SQL은 역할에 따라 나눠 볼 수 있습니다.

  • DDL(Data Definition Language): 스키마나 테이블 같은 구조를 만들고 바꿉니다.
  • DML(Data Manipulation Language): 저장된 행을 조회·추가·수정·삭제합니다.

이 글에서는 교안의 분류에 따라 SELECT, INSERT, UPDATE, DELETE를 DML로 묶어 설명합니다.

PostgreSQL, MySQL, Oracle, SQL Server는 모두 RDBMS 제품입니다. 오늘 예습에서는 제품별 성능이나 우열을 비교하지 않습니다.

상세 설명

감자 식당 주문 장부실 만들기

예시를 짧게 만들기 위해 주문 한 행에는 메뉴 하나만 담겠습니다. 실제 서비스에서 주문 하나에 여러 메뉴를 담으려면 주문과 주문 항목을 다시 나눌 수 있습니다.

먼저 ERD에 다음 관계를 그렸다고 생각해 봅시다.

  • 고객 한 명은 주문을 여러 개 남길 수 있습니다.
  • 메뉴 하나는 여러 주문에 등장할 수 있습니다.
  • 주문 한 건은 고객 한 명과 메뉴 하나를 가리킵니다.

코드 읽기 · INTEGER는 정수, TEXT는 글자, NOT NULL은 값 필수, REFERENCES는 다른 키 가리키기, CHECK는 조건 검사입니다.

-- Step 1 — 관계 설계
-- customers 1:N orders, menu_items 1:N orders

-- Step 2 — 스키마 구역
CREATE SCHEMA potato_shop;

-- Step 3 — DDL 구조 만들기
CREATE TABLE potato_shop.customers (
  customer_id INTEGER PRIMARY KEY,
  name TEXT NOT NULL
);

CREATE TABLE potato_shop.menu_items (
  menu_id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  price INTEGER NOT NULL CHECK (price >= 0)
);

CREATE TABLE potato_shop.orders (
  order_id INTEGER PRIMARY KEY,
  customer_id INTEGER NOT NULL
    REFERENCES potato_shop.customers(customer_id),
  menu_id INTEGER NOT NULL
    REFERENCES potato_shop.menu_items(menu_id),
  quantity INTEGER NOT NULL CHECK (quantity > 0)
);

-- Step 4 — DML 기록 다루기
INSERT INTO potato_shop.customers (customer_id, name)
VALUES (1, '김감자');

INSERT INTO potato_shop.menu_items (menu_id, name, price)
VALUES (10, '감자튀김', 3000);

INSERT INTO potato_shop.orders
  (order_id, customer_id, menu_id, quantity)
VALUES
  (1001, 1, 10, 2);

SELECT order_id, customer_id, menu_id, quantity
FROM potato_shop.orders
WHERE order_id = 1001;

코드는 다음 순서로 움직입니다.

  1. Step 1 — 관계 설계: ERD에서 고객·메뉴·주문의 연결 규칙을 정합니다.
  2. Step 2 — 스키마 구역: potato_shop이라는 이름 아래 관련 테이블을 모읍니다.
  3. Step 3 — DDL 구조 만들기: 세 테이블과 PK·FK·수량 규칙을 만듭니다.
  4. Step 4 — DML 기록 다루기: 고객과 메뉴를 넣고, 두 기록을 가리키는 주문을 저장한 뒤 조회합니다.

예를 들어 고객 장부에 99번이 없는데 주문에 customer_id = 99를 적으면, DBMS가 **“99번 손님은 아직 이 세계관에 없습니다.”**라며 주문 행을 거절합니다. 이 검사는 orders.customer_id에 REFERENCES로 FK 제약조건을 실제 선언했기 때문에 일어납니다. 번호가 우연히 같다고 자동으로 연결되지는 않습니다.

장부 비유는 테이블의 역할을 나누고 키로 연결하는 데까지만 맞습니다. 실제 DBMS는 종이 서랍장이 아니며, 동시 작업·권한·복구 같은 기능도 함께 처리합니다.
