RAG·LoRA·Quantization으로 서비스 나누기

Day 02. 지식·행동·입력·자원 문제를 따로 풀기

예정 강의일 · 2026.08.31

오늘 만들 것

어제 만든 LoRA adapter 후보를 직원용 HR 질문 서비스에 연결합니다. 질문이 들어올 때 문서를 찾는 RAG, 긴 입력을 줄이는 Context Compression, 답변 방식을 맞추는 LoRA, 실행 자원을 줄이는 Quantization의 자리를 나눕니다.

왜 필요한가

네 기술은 모두 “모델을 더 잘 쓰는 법”처럼 보이지만 해결하는 문제가 다릅니다. 한 기술이 다른 문제까지 자동으로 해결한다고 기대하면 서비스의 약점을 놓치기 쉽습니다.

전체 흐름과 오늘의 경계

질문과 문서 → 필요한 문맥 → Base+LoRA 모델 → 답변 → 평가만 따라갑니다. API 구현, 배포 코드와 운영 자동화는 본수업에 남겨 둡니다.

지난 수업 복습

Day 01에서는 Base Model을 고정한 채 작은 LoRA adapter를 학습했습니다. train으로 학습하고 validation으로 선택한 뒤, evaluation에서 Base와 adapter를 같은 조건으로 비교했습니다.

LoRA adapter는 답변 형식이나 작업 패턴을 학습한 숫자 update입니다. 최신 규정 문서를 실시간으로 보관하는 창고가 아닙니다. 오늘은 이 빈자리를 다른 기술과 연결합니다.

오늘 수업에서 꼭 가져가야 할 것

RAG·LoRA·Context Compression·Quantization은 서비스의 어느 문제를 풀며, 한 흐름에서 어떻게 연결될까?

1. RAG는 답할 때 외부 문서를 가져온다

낯선 말 3개눌러서 뜻 보기
query

사용자가 서비스에 보낸 질문이나 검색 요청.

retrieval

query와 관련 있는 문서 조각을 찾아오는 과정.

context

모델이 현재 답을 만들 때 함께 참고하도록 받은 입력 정보.

**RAG(Retrieval-Augmented Generation)**는 질문이 들어온 시점에 관련 문서를 retrieval하고, 찾은 내용을 context로 넣어 답을 생성하는 방식입니다. 감자 우체국에서는 문서 보관실에서 관련 규정 봉투를 찾아 처리실로 가져오는 일에 해당합니다.

RAG는 보통 model parameter를 다시 학습시키는 방법이 아닙니다. 문서가 업데이트됐다면 검색 대상과 색인도 함께 최신으로 바꿔야 합니다. 잘못 찾은 문서나 문서에 없는 답까지 자동으로 막아 주지는 않습니다.

2. Context Compression은 모델에 넣을 입력을 줄인다

Context Compression은 찾은 문서 전체를 무조건 넣는 대신 질문에 필요한 부분을 고르거나 줄여 모델 입력을 정리하는 접근입니다. 우체국 비유에서는 가져온 규정 봉투에서 이번 질문에 필요한 쪽만 전달하는 일입니다.

입력이 짧아지면 처리할 양도 줄어듭니다. 하지만 필요한 예외 조항을 버리면 답이 나빠질 수 있습니다. “짧게 만들었다”와 “필요한 정보가 모두 남았다”는 같은 말이 아닙니다.

3. LoRA는 답변 행동을, Quantization은 숫자 표현을 바꾼다

LoRA는 Day 01에서 만든 adapter를 Base Model에 적용해 답변 형식과 작업 패턴을 바꾸는 역할입니다. RAG가 가져온 최신 문서를 adapter 안에 저장하는 것은 아닙니다.

**Quantization(양자화)**은 model weight 같은 숫자를 더 낮은 정밀도로 표현해 모델을 불러오고 실행할 때 필요한 memory를 줄이는 방법입니다. 감자 우체국에서는 처리기의 숫자표를 더 짧은 칸으로 기록하는 장면으로 기억해 둡니다.

규정 봉투와 짧은 숫자표는 오늘 역할을 구분하는 보조 장면일 뿐, 감자 우체국의 새 고정 대응은 아닙니다. 실제 기술의 이름과 바꾸는 대상을 먼저 기억하면 됩니다.

낯선 말 1개눌러서 뜻 보기
memory

프로그램과 model이 실행 중 데이터를 올려 두는 저장 공간.

Quantization은 모델을 더 똑똑하게 만드는 학습이 아닙니다. memory 사용량은 줄일 수 있지만 정확도와 속도 변화는 방법, hardware와 구현에 따라 달라질 수 있으므로 실제 환경에서 확인해야 합니다.

서비스 평가는 한 점수로 끝내지 않습니다. 필요한 문서를 찾았는지, 답이 질문과 문서에 맞는지, latency와 memory가 운영 조건을 만족하는지를 나누어 봅니다. Fine-Tuning, RAG와 Quantization을 사용했다는 사실만으로 사실성·개인정보 보호·최신성·안전성이 증명되지는 않습니다.

상세 설명

연차 신청은 어디에서 하나요?가 답이 되기까지

감자 우체국의 문서 보관실과 문장 처리실을 한 서비스로 연결합니다.

Quantization은 답을 만든 뒤 덧붙이는 단계가 아닙니다. 요청을 받기 전에 배포 환경에 맞는 정밀도로 모델을 불러오는 실행 구성을 먼저 정합니다.

  1. 실행 준비: 배포 환경에 맞는 Quantization을 선택하고 Base Model과 LoRA adapter를 불러옵니다.
  2. 질문 받기: query를 받고 무엇을 묻는지 확인합니다.
  3. 문서 찾기: RAG retrieval이 관련 HR 규정 조각을 가져옵니다.
  4. 입력 정리: Context Compression이 질문에 필요한 부분을 남깁니다.
  5. 답 만들기: 준비한 Base Model과 LoRA adapter가 정리된 context를 참고해 답합니다.
  6. 결과 확인: 검색과 답변 품질, latency와 memory를 각각 측정하고 실패 사례를 확인합니다.

이 목록은 네 기술이 언제나 모두 필요한 필수 공식이 아닙니다. 문서가 거의 바뀌지 않거나 입력이 짧고 자원이 충분한 서비스라면 필요한 조합도 달라집니다.
