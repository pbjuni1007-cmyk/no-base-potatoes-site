Docker Compose

Day 02. 여러 container를 연결해 한 application으로 실행하기

예정 강의일 · 2026.08.24

오늘 만들 것

감자랜드 이동식 푸드코트에는 주문 창구(Frontend), 요청을 처리하는 주방(Backend), 재고를 조회·갱신하는 관리 데스크(Database)가 필요합니다. 가게별 container를 따로 열 수는 있지만, 명령과 연결 설정을 매번 반복하면 하나를 빠뜨리기 쉽습니다.

오늘은 세 역할을 compose.yaml에 적고, network·volume·health 조건을 연결해 docker compose up 한 번으로 함께 시작합니다.

왜 필요한가

container가 여러 개면 image 이름뿐 아니라 port, 환경 변수, 저장 공간, 통신 경로와 시작 조건도 함께 맞아야 합니다. Docker Compose는 이 구성을 한 파일에 적고 application 단위로 실행합니다.

지난 수업 복습

Day 01에서는 Dockerfile로 image를 만들고 그 image에서 container를 시작했습니다. Frontend·Backend·Database도 각각 실행에 필요한 파일과 기본값을 image로 준비합니다.

container를 docker run으로 하나씩 시작하면 port, 환경 변수, network와 volume 설정도 각각 명령에 적어야 합니다. 오늘은 이 반복 설정을 하나의 Compose file로 옮깁니다.

낯선 말 2개눌러서 뜻 보기
multi-container application

역할별 container 여러 개가 같은 network 안에서 함께 작동하는 하나의 application.

YAML

들여쓰기로 항목의 포함 관계를 나타내는 설정 파일 형식.

YAML에서는 들여쓰기가 꾸밈이 아니라 구조입니다. 같은 깊이의 frontend, backend, database는 나란한 service이고, 그 아래 들여쓴 값은 해당 service의 설정입니다.

오늘 수업에서 꼭 가져가야 할 것

따로 실행하던 Frontend·Backend·Database container를 서로 연결되고 준비 상태를 확인할 수 있는 하나의 Compose application으로 어떻게 묶을까요?

1. Compose file과 service: 여러 실행 설정을 한곳에 적습니다

Compose file은 여러 service와 공용 network·volume을 선언하는 합동 운영표입니다. 여러 host에 container를 배치하는 Kubernetes 같은 orchestrator를 대신하는 파일은 아닙니다.

service는 Compose가 같은 image와 실행 설정으로 관리하는 application 구성 단위입니다. frontend, backend, database라는 service마다 사용할 image, 환경 변수와 연결 대상을 적습니다.

2. network와 service 이름: container끼리 서로 찾게 합니다

같은 Compose network에 연결된 service는 service 이름으로 서로를 찾을 수 있습니다.

낯선 말 2개눌러서 뜻 보기
DNS

database 같은 이름을 통신에 사용할 주소로 찾아 주는 기능.

localhost

현재 프로그램이 실행되는 바로 그 컴퓨터나 container 자신을 가리키는 이름.

backend container 안에서 localhost:5432는 database가 아니라 backend 자신입니다. Database에는 database:5432처럼 service 이름으로 연결합니다.

브라우저는 Compose network 밖에서 실행됩니다. 사용자는 Host에 공개된 Frontend port로 접속합니다. Frontend container의 웹 서버가 내부에서 Backend로 요청을 전달할 때는 backend라는 service 이름을 쓸 수 있습니다.

3. environment·ports·volumes: 바깥값과 수명을 연결합니다

environment는 service container에 실행 설정을 전달합니다. ports는 Host와 container의 port를 연결합니다. 내부 service 통신에 무조건 Host port를 공개할 필요는 없습니다.

volumes는 Database data가 container 교체와 별개로 남도록 외부 저장실을 연결합니다. Database service는 data를 읽고 쓰는 프로그램이고, volume은 그 프로그램이 사용하는 저장 공간입니다.

4. healthcheck와 depends_on: 시작됨과 준비됨을 구분합니다

service process가 시작됐다고 곧바로 요청을 처리할 준비가 된 것은 아닙니다. healthcheck는 service 안에서 명령을 실행해 정상 응답 여부를 확인합니다.

depends_on의 짧은 표기는 service 시작 순서를 표현하지만 건강 상태까지 기다리지 않습니다. 의존 service에 healthcheck를 두고 condition: service_healthy를 사용해야 준비 상태를 기다릴 수 있습니다.

5. docker compose up: 선언한 application을 함께 시작합니다

docker compose up은 필요한 container와 network를 만들고 service를 시작합니다. 한 명령으로 실행하더라도 내부에서는 각 service가 별도 container로 동작하며, 로그와 실패 상태도 service별로 확인해야 합니다.

상세 설명

Step 1. 세 service를 Compose file에 적습니다

Day 01에서 potato-frontend:1.0과 potato-api:1.0 image를 만들었다고 가정합니다. Database는 PostgreSQL image를 사용합니다.

services:
  frontend:
    image: potato-frontend:1.0
    ports:
      - "3000:80"
    networks:
      - potato-net

  backend:
    image: potato-api:1.0
    environment:
      DB_URL: jdbc:postgresql://database:5432/potato
    depends_on:
      database:
        condition: service_healthy
    networks:
      - potato-net

  database:
    image: postgres:17
    environment:
      POSTGRES_DB: potato
      POSTGRES_USER: potato
      POSTGRES_PASSWORD: example-only
    volumes:
      - potato-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U potato -d potato"]
      interval: 5s
      timeout: 3s
      retries: 10
    networks:
      - potato-net

networks:
  potato-net:

volumes:
  potato-data:

POSTGRES_PASSWORD의 example-only는 학습용 예시값입니다. 실제 자격 증명을 원고나 저장소에 넣지 않습니다.

Step 2. 연결 관계를 따라갑니다

  1. Host → Frontend: 브라우저는 localhost:3000으로 들어오고 ports가 Frontend container의 80번 port로 전달합니다.
  2. Backend → Database: Backend의 DB_URL은 database:5432를 사용합니다. database는 같은 network의 service 이름입니다.
  3. Database → volume: PostgreSQL이 /var/lib/postgresql/data에 쓴 내용은 potato-data volume에 남습니다.
  4. 준비 확인: Database의 pg_isready가 성공해 healthy가 된 뒤 Backend가 시작됩니다.

Step 3. application을 시작합니다

docker compose up

Compose는 file에 선언한 service와 연결 관계를 읽어 application을 시작합니다. 정상 흐름은 다음과 같습니다.

database healthcheck 성공 → backend 시작 → Host가 frontend:3000 접속 → service들이 potato-net에서 통신

depends_on은 application 시작 때의 의존 순서를 돕지만, 실행 중 service가 잠시 실패했을 때 업무 요청이 반드시 성공하도록 보장하지는 않습니다. 재시도와 장애 복구는 별도 설계입니다.

스스로 확인

Q1 · container 사이 주소 고르기

backend와 database가 같은 Compose network에 있을 때 DB_URL에 들어갈 알맞은 주소는 무엇일까요?

services:
  backend:
    environment:
      DB_URL: jdbc:postgresql://database:5432/potato
  database:
    image: postgres:17
container 안의 localhost는 그 container 자신이고, 같은 network의 다른 service는 service 이름으로 찾습니다.

Q2 · 시작 순서와 준비 상태 연결하기

backend가 database의 실제 준비 상태를 기다리게 하는 두 설정을 연결해 봅시다.

database service에는 정상 응답을 검사하는 를 두고, backend의 depends_on에는 condition을 로 지정합니다.

선택 설명 · 필요할 때 펼쳐보기

선택 설명 · rootfs와 image layer

선택 용어 · rootfs — container process가 /부터 보게 되는 실행용 파일과 폴더 구조.

선택 용어 · image layer — 이전 filesystem에 추가·수정·삭제할 파일 변화를 기록한 읽기 전용 묶음.

image는 완성 폴더 하나만 저장하는 것이 아니라, 파일 변화 layer와 실행 설정을 함께 가집니다. container가 시작되면 이 layer들이 process가 볼 rootfs의 바탕이 되고, 실행 중 변경은 별도의 쓰기 영역에 생깁니다.

이 설명은 Compose file을 읽기 위한 필수 지식은 아닙니다. image가 단순한 압축 파일 하나도 아니고 실행 중인 process도 아니라는 경계만 보충합니다.

선택 설명 · namespace와 cgroup

선택 용어 · namespace — process가 PID·network·mount 같은 system 자원을 자기 범위 안에서 따로 보게 하는 Linux kernel 기능.

선택 용어 · cgroup — process를 묶어 CPU·memory 같은 자원의 사용량을 관찰하고 제한하는 Linux kernel 기능.

namespace는 주로 무엇을 따로 보게 할지, cgroup은 자원을 얼마나 쓰게 할지를 다룹니다. Docker는 이런 기능을 조합해 container process의 실행 범위를 나눕니다.

그래도 container가 완전히 독립된 작은 VM이 되는 것은 아닙니다. 같은 실행 환경의 Linux kernel을 공유하며, 실제 보안은 사용자·권한·network와 추가 보안 설정까지 함께 봐야 합니다.
