오늘 만들 것

감자랜드 AI 고객센터의 Service가 예약 안내 문장을 ChatClient에 보내고, AI 모델이 만든 텍스트 한 줄을 받아 옵니다. 오늘의 핵심은 기능을 많이 붙이는 것이 아니라 Spring Boot 코드와 AI 모델이 어디에서 연결되는지 읽는 것입니다. ChatClient가 있으면 Service가 모델별 호출 방법을 하나하나 다루지 않아도 됩니다. 요청 작성부터 응답 텍스트를 꺼내는 일까지 한곳에서 맡기기 때문입니다.

지난 Spring 수업의 계층은 한 줄만 떠올리면 됩니다.

Controller → Service → Repository는 요청 접수, 업무 처리, 데이터 접근 역할을 나눕니다.

오늘은 그중 Service가 ChatClient를 호출하는 연결 하나를 추가합니다. API 키는 모델 호출에 필요한 설정이지만 코드에 직접 적거나 화면에 공개하지 않습니다.

오늘 수업에서 꼭 가져가야 할 것

한 관계: Service와 모델 사이의 ChatClient

Spring AI는 AI 모델 자체가 아닙니다. Spring 애플리케이션이 여러 AI 모델을 호출하도록 공통 API를 제공하는 프레임워크입니다.

ChatClient는 Service와 모델 사이에서 다음 일을 잇습니다.

Service는 “무엇을 물을지” 정합니다. ChatClient는 그 요청을 조립해 AI 모델에 전달하고, 모델이 만든 텍스트를 Service가 받을 수 있게 잇습니다.

한 대비: System과 User

둘 다 프롬프트(prompt), 즉 모델에 보내는 지시와 자료의 일부입니다. System은 매 호출에 적용할 공통 규칙, User는 이번 질문이나 자료라는 차이만 먼저 잡으면 됩니다.

상세 설명

짧은 코드로 호출 흐름 읽기

아래 코드는 Service 안의 핵심 호출만 남긴 Java 예시입니다.

String summarize(String reservation) {
    return chatClient.prompt()
            .system("예약 사실만 한국어 한 문장으로 답하세요.")
            .user(reservation)
            .call()
            .content();
}

메서드 이름을 위에서 아래로 읽으면 됩니다.

  1. prompt() — 모델에 보낼 요청 작성을 시작합니다.
  2. system(...) — 공통 역할과 규칙을 넣습니다.
  3. user(...) — 이번 질문이나 자료를 넣습니다.
  4. call() — 스트리밍이 아닌 동기 호출 경로를 고릅니다. 이 줄만으로 모델을 실행하지는 않습니다.
  5. content() — 실제 모델 호출을 실행하고 응답의 텍스트를 돌려줍니다.

코드의 중심 흐름은 Service → prompt → system/user → call → content → 텍스트 응답입니다. call()로 동기 경로를 고른 뒤, 마지막 content()까지 이어져야 실제 모델 호출과 문자열 반환이 일어난다고 읽습니다.

여기부터는 오늘의 연결을 이해한 뒤 필요할 때 펼쳐 보는 내용입니다. R-101과 CR-201 상태 연속성도 시리즈 소품이며 필수 선수지식은 아닙니다.

호출 전에 확인할 것

R-101 요약을 요청받았다고 바로 예약 정보를 Prompt에 넣지 않습니다. 먼저 로그인한 사용자인지 확인하고, 그 사용자가 R-101을 볼 권한이 있는지 검사한 뒤, 소유자 조건이 포함된 조회로 허용된 필드만 가져옵니다.

요청 → 인증 → 인가·소유자 조회 → 허용된 사실 → ChatClient 순서를 지키면 접근 거부될 데이터가 모델 호출에 먼저 들어가는 일을 막을 수 있습니다. Prompt에서 “다른 사용자의 예약은 보지 마”라고 말하는 것은 앱의 권한 검사를 대신하지 않습니다.

응답을 어떤 모양으로 받을지

옆으로 밀어서 비교 →
terminal method앱이 받는 것이어서 확인할 것
content()모델 답의 문자열빈 답인지, 원본 사실과 맞는지
chatResponse()답과 token 사용량 같은 metadata필요한 metadata만 쓰고 민감정보를 남기지 않는지
entity(MyType.class)문자열을 지정한 Java 타입으로 변환한 값구조 변환 성공 뒤에도 값과 업무 규칙이 맞는지

Spring AI 2.0의 fluent API에서는 call()만 호출해도 모델 실행이 시작되는 것이 아닙니다. call()은 동기 호출 경로를 고르고, content(), chatResponse(), entity() 같은 반환 메서드가 실제 모델 호출을 실행해 필요한 모양으로 결과를 돌려줍니다. Java 객체로 변환됐다는 사실은 구조 변환에 성공했다는 뜻에 가깝고, 예약 번호와 상태가 실제 DB 사실이라는 보장은 아닙니다.

실패를 한 덩어리로 숨기지 않기

옆으로 밀어서 비교 →
상황보통 구분할 HTTP 상태fallback 판단
로그인 정보가 없음401성공 응답으로 바꾸지 않음
로그인했지만 R-101 권한이 없음403성공 응답으로 바꾸지 않음
허용된 범위에서 R-101을 찾지 못함404없는 예약을 만들어 내지 않음
모델 호출 한도를 잠시 넘김429이미 인가한 비AI 자료가 있을 때만 검토
모델 제공자나 서버가 일시 장애503이미 인가한 비AI 자료가 있을 때만 검토

fallback은 실패를 성공처럼 칠하는 문구가 아닙니다. 예를 들어 인가를 통과한 예약의 고정 안내문을 대신 보여 줄 수는 있지만, 401·403·404나 모델의 사실 불일치를 “AI가 잠시 바빠요”로 덮어서는 안 됩니다.

이 안전장치들은 삭제된 것이 아닙니다. 다만 오늘 자가점검은 Spring AI 호출의 첫 연결만 확인하므로 정답으로 묻지 않습니다.
