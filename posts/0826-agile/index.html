막연한 요구사항을 이번 Sprint에서 실행할 일로 어떻게 바꾸는가?

1. Agile: 계획을 버리지 않고 새 정보에 맞춰 고칩니다

Agile은 처음 세운 계획을 끝까지 지키는 것보다, 작은 결과를 자주 확인하고 다음 계획을 조정하는 접근입니다. 계획과 문서를 없애자는 뜻이 아닙니다. 지금 필요한 만큼 계획하고, 실제 결과에서 배운 내용으로 순서와 방법을 바꿉니다.

낯선 말 1개눌러서 뜻 보기
피드백

만든 결과를 본 뒤 다음 계획을 고치는 데 쓰는 반응과 정보.

감자대학교도 모든 수강 기능을 한꺼번에 계획하지 않습니다. 먼저 강의 신청과 결과 확인이라는 작은 결과를 정하고, 구현 뒤 확인한 문제를 다음 계획에 반영합니다.

2. Scrum과 Sprint: 적응을 반복할 작업 틀을 만듭니다

Scrum은 복잡한 일을 짧은 Sprint로 반복하며 결과를 확인하고 다음 계획을 조정하도록, 팀의 책무·이벤트·산출물을 정한 가벼운 프레임워크입니다.

낯선 말 1개눌러서 뜻 보기
프레임워크(Framework)

일을 진행할 때 반복해서 사용할 역할, 순서와 기본 규칙의 틀.

Scrum에서는 Sprint라는 고정된 길이의 반복 안에서 목표를 정하고, 쓸 수 있는 결과를 만들고, 확인한 내용에 맞춰 다음 행동을 조정합니다. Sprint는 한 달 이하이며 팀이 일정한 길이를 선택합니다. 이 수업이 이틀이라고 실제 Sprint도 반드시 이틀인 것은 아닙니다.

낯선 말 1개눌러서 뜻 보기
타임박스(Timebox)

한 활동에 쓸 수 있는 최대 시간을 미리 정해 집중하는 방식.

3. User Story와 Acceptance Criteria: 요청을 결과와 확인 조건으로 바꿉니다

User Story는 기능을 누가, 무엇을 원하고, 왜 필요한지 짧게 적는 대화의 출발점입니다. 완전한 계약서나 상세 설계서는 아닙니다.

US-ENR-01의 User Story는 다음과 같습니다.

수강생으로서 원하는 강의를 신청하고 결과를 확인하고 싶다.

Acceptance Criteria, 즉 인수 기준은 이 요청 카드가 기대한 동작을 했는지 확인하는 조건입니다. 과목을 확인할 수 있다, 같은 강의를 두 번 신청하지 않는다, 성공하면 신청 결과를 확인할 수 있다처럼 관찰 가능한 문장으로 적습니다. 어느 클래스와 DB 테이블을 쓸지는 아직 정하지 않아도 됩니다.

4. Product Backlog: 앞으로 할 일 전체의 순서를 관리합니다

Product Backlog는 제품을 더 낫게 만드는 데 필요한 일을 순서대로 둔 목록입니다. 처음부터 완성된 고정 계약서가 아닙니다. 새로 배운 내용에 따라 항목과 순서가 달라질 수 있습니다.

낯선 말 1개눌러서 뜻 보기
우선순위

무엇을 먼저 검토하고 실행할지 나타내는 순서.

감자대학교의 전체 목록에는 강의 목록 보기, 수강신청, 신청 완료 알림이 함께 있을 수 있습니다. 그중 사용자에게 먼저 필요한 결과, 실패 위험과 다른 작업의 선후 관계를 보고 US-ENR-01을 앞쪽에 둡니다. Product Backlog는 이번 Sprint에 하겠다고 확정한 목록이 아닙니다.

5. Sprint Goal과 Sprint Backlog: 이번 반복의 목적과 계획을 고릅니다

Sprint Goal은 이번 Sprint가 왜 필요한지 한 문장으로 정한 목적입니다.

수강생이 같은 강의를 중복 신청하지 않고 신청 결과를 확인한다.

Sprint Backlog에는 세 가지가 함께 들어갑니다.

  1. 왜: Sprint Goal
  2. 무엇을: 이번 Sprint에 고른 Product Backlog 항목
  3. 어떻게: 그 항목을 끝내기 위한 실행 계획

Task는 실행 계획을 팀이 바로 움직일 만큼 구체적으로 나눈 일입니다. 과목 신청 가능 여부 확인, 중복 신청 검사, 신청 결과 저장, 인수 기준 검사처럼 적을 수 있습니다. Task 목록은 시작 전에 영원히 고정되는 약속이 아닙니다. Sprint Goal을 지키는 범위에서 구현하며 더 나은 계획으로 고칠 수 있습니다.

Product Backlog가 앞으로 할 일 전체의 순서라면, Sprint Backlog는 이번 Sprint의 목표, 선택한 항목과 실행 계획입니다. 이름은 비슷하지만 범위와 쓰임이 다릅니다.

상세 설명

1단계 · 한 줄 요청에서 빠진 것을 찾기

처음 문장은 수강신청 기능 개발뿐이었습니다. 이 문장만 보고 바로 코드를 나누면 다음 질문에 답할 수 없습니다.

  • 누가 이 기능을 쓰는가?
  • 사용자는 어떤 결과를 얻어야 하는가?
  • 신청할 수 없는 과목이면 어떻게 보이는가?
  • 같은 강의를 다시 신청하면 성공인가, 실패인가?
  • 무엇이 보이면 이번 기능을 확인했다고 말할 수 있는가?

이 질문은 개발을 늦추는 잡담이 아닙니다. 서로 다른 완성 모습을 떠올린 채 코드를 만드는 일을 줄입니다.

3단계 · 확인 가능한 조건 붙이기

US-ENR-01의 최소 Acceptance Criteria를 다음처럼 정합니다.

  1. 선택한 과목이 존재하고 신청 가능한지 확인한다.
  2. 같은 수강생이 같은 과목을 이미 신청했다면 새 신청을 만들지 않고 이유를 알려 준다.
  3. 신청에 성공하면 완료 여부와 신청 결과를 보여 준다.

조건은 내부 구현 순서가 아니라 바깥에서 확인할 동작을 말합니다. if문을 두 개 쓴다나 enrollment 테이블에 INSERT한다는 구현 Task가 될 수 있지만, 사용자가 기대한 결과를 설명하는 인수 기준은 아닙니다.

이제 Product Backlog 전체를 복사하지 않고, Sprint Goal에 필요한 항목과 실행 계획만 Sprint Backlog에 둡니다.

Sprint Goal

US-ENR-01 · 강의 신청과 결과 확인

실행 계획
- 과목이 신청 가능한지 확인한다.
- 중복 신청인지 확인한다.
- 신청 결과를 저장하고 반환한다.

이 작업판은 누가 몇 시까지 무엇을 한다는 감시표가 아닙니다. 팀이 Sprint Goal을 향해 현재 계획과 진행을 함께 볼 수 있게 하는 도구입니다. 구현 중 더 필요한 Task를 발견하면 계획을 구체화할 수 있습니다.

선택 설명 1 · Agile과 Waterfall은 상황을 보고 고릅니다

선택 용어 · Waterfall — 요구 분석, 설계, 구현과 검증 같은 단계를 앞에서 뒤로 진행하는 접근.

Agile이 언제나 빠르고 Waterfall이 언제나 낡았다는 뜻은 아닙니다. 중요한 차이는 멋진 방법론 이름이 아니라 언제 피드백을 받고 계획을 바꿀지입니다.

피드백동작하는 작은 결과마다 자주 받음정해진 단계의 결과를 기준으로 확인
어울릴 수 있는 상황요구와 해결 방법의 변화가 잦음요구가 안정적이고 변경 비용이 매우 큼

예를 들어 학생이 실제로 써 보며 화면을 고쳐야 하는 수강신청 경험은 짧은 결과와 피드백이 유용합니다. 반대로 법이나 계약으로 출력 형식과 승인 절차가 이미 강하게 고정된 작업은 앞단의 명세와 단계별 승인이 더 중요할 수 있습니다. 실제 조직은 두 접근을 섞기도 합니다. Agile=계획 없음, Waterfall=피드백 없음으로 외우지 말고 변화 가능성과 검증 비용을 비교해야 합니다.

선택 설명 2 · 공식 Scrum 요소와 현장 관행을 구분합니다

선택 용어 · Scrum accountability — Scrum Team에서 특정 결과에 책임지는 구분.

선택 용어 · Scrum event — 검사와 적응을 위해 정해 둔 공식 활동.

선택 용어 · Scrum artifact — 일과 가치가 어떻게 진행되는지 투명하게 보여 주는 공식 결과물.

Scrum Guide 2020이 정한 큰 틀은 다음과 같습니다.

옆으로 밀어서 비교 →
구분공식 요소
accountabilitiesProduct Owner, Scrum Master, Developers
eventsSprint, Sprint Planning, Daily Scrum, Sprint Review, Sprint Retrospective

Daily Scrum은 Developers가 Sprint Goal을 향한 진행을 확인하고 다음 계획을 조정하는 행사입니다. 상사에게 보고하는 회의가 아니며, 서서 진행하거나 어제·오늘·장애물 세 질문을 쓰는 형식도 필수 규칙은 아닙니다. Backlog Refinement는 Product Backlog를 계속 작고 분명하게 다듬는 활동이지만 별도의 공식 event는 아닙니다.

User Story, Acceptance Criteria, Task로 계획을 나누는 방식, INVEST, MoSCoW, Story Point, Planning Poker, Kanban Board, Velocity와 Burndown Chart는 현장에서 도움을 줄 수 있는 선택 도구입니다. 이 글에서 User Story와 Task를 쓴 이유도 사용자 가치와 실행 계획을 보기 좋게 나누기 위해서이지, Scrum이 그 형식을 강제하기 때문이 아닙니다. Sprint 0 역시 준비 단계를 부르는 현장 표현일 수 있지만 공식 Scrum 요소는 아닙니다.

선택 설명 3 · Acceptance Criteria와 Definition of Done은 확인 대상이 다릅니다

선택 용어 · Definition of Done(DoD) — Increment가 완료됐다고 인정받기 위해 만족해야 하는 공통 품질 기준.

둘 다 완료를 확인하지만 같은 체크리스트는 아닙니다.

Acceptance Criteria가 모두 맞아도 공통 테스트나 품질 기준을 통과하지 못했다면 완료된 Increment로 볼 수 없습니다. 반대로 DoD만 적어 놓고 중복 신청을 막는다는 기능별 기대 동작을 확인하지 않으면 엉뚱한 기능을 품질 좋게 만들 수 있습니다. 기능별 동작과 공통 품질을 서로 다른 층에서 확인해야 합니다.
