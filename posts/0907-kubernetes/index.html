내 앱은 쿠버네티스 안에서 어디서, 어떻게 실행될까?

Day 01. 앱의 실행 위치와 관리 역할 이해하기

예정 강의일 · 2026.09.07

감자랜드 이동식 푸드코트의 주문 조회 앱을 떠올려 봅시다. 주문 번호를 보내면 “감자튀김 두 개, 준비 중”이라고 답해 주는 프로그램입니다. 지금은 내 컴퓨터에서 실행하지만, 내 컴퓨터를 꺼도 사람들이 계속 이용하게 하려면 앱을 맡아 실행할 별도 컴퓨터가 필요합니다.

그런데 앱을 세 개 띄워 두었다가 하나가 사라지면 누가 다시 만들까요? 새 앱은 어느 컴퓨터에서 실행할까요? 쿠버네티스는 앱의 기능을 만드는 도구가 아니라, 이렇게 앱을 실행하고 유지하는 일을 관리하는 시스템입니다.

이 글에서는 설치나 명령 실행 없이, 수업에서 나올 이름들이 이 과정의 어디에 있는지 먼저 연결합니다.

지난 수업 복습

Docker·Compose 수업의 출발점은 “내 컴퓨터 밖에서도 앱을 실행하려면 무엇을 전달해야 할까?”였습니다. 아직 기억이 흐릿해도 다음 차이부터 잡으면 됩니다.

코드는 프로그램의 일을 적어 둔 파일입니다. 그 파일을 실행하면 컴퓨터가 명령을 수행하기 시작합니다. 이렇게 실행 중인 프로그램을 프로세스(process)라고 합니다. 주문 조회 앱은 주문 번호를 받으면 조회 결과를 돌려주는 프로세스로 일합니다.

상대 프로그램에게 처리를 부탁하는 메시지가 요청, 돌아온 결과가 응답입니다. 요청을 받아 응답하는 프로그램을 서버라고 하며, 문맥에 따라 그 프로그램이 돌아가는 컴퓨터도 서버라고 부릅니다. 이 글에서는 컴퓨터를 말할 때 따로 표시합니다.

코드 파일만 다른 컴퓨터로 옮기면, 그 컴퓨터에 실행에 필요한 프로그램이나 파일이 없을 수 있습니다. Docker는 이 실행 조건을 묶고 시작하는 데 쓰입니다.

image

앱을 시작하는 데 필요한 파일과 기본 실행 설정을 묶어 둔 것. 이미지라고 읽습니다.

낯선 말 1개눌러서 뜻 보기
container

이미지의 파일·설정으로 시작한, 다른 실행과 구분된 환경에서 일하는 프로세스. 컨테이너라고 읽습니다.

푸드코트 비유에서 이미지는 봉인된 표준 가게 세트, 컨테이너는 그 세트로 실제 문을 연 가게입니다. 같은 세트로 여러 가게를 열듯, 같은 이미지로 컨테이너를 여러 개 실행할 수 있습니다. 다만 컨테이너는 물리 상자나 작은 컴퓨터가 아니며, 이 비유가 완전한 보안 분리를 뜻하지는 않습니다.

이미지를 만드는 지시서가 Dockerfile, 그 지시서에 따라 이미지를 만드는 과정이 빌드(build)입니다. 지난 Compose 수업은 여러 앱의 실행·연결 설정을 한 파일에 모으는 데까지 이어졌습니다. 오늘은 그 앱들을 여러 컴퓨터에 배치하고 유지하는 문제로 넘어갑니다.

오늘 수업에서 꼭 가져가야 할 것

내 앱이 쿠버네티스 안에서 실행된다는 것은 무슨 뜻이고, 누가 어떤 역할을 맡을까요?

수업에서는 무엇을 실행하는지, 어디에 놓는지, 누가 원하는 상태로 맞추는지를 나누어 들으면 됩니다. 앱의 실행 위치를 이해한 뒤에는 “켜졌다”와 “사용할 준비가 됐다”의 차이, 그리고 내가 조작하려는 대상이 어디인지까지 연결해 보겠습니다.

상세 설명

1. 내 컴퓨터의 앱을 다른 곳에서도 실행하려면

앱을 실행할 환경에 준비해서 사용할 수 있게 하는 과정을 배포라고 합니다. 파일을 올리는 일만도, 프로그램을 한 번 켜는 일만도 아닙니다. 필요한 설정을 갖추고, 사용자가 접속할 길도 마련해야 합니다. 오늘은 그중 앱을 실행하고 유지하는 부분부터 이해합니다.

우리 주문 조회 앱의 이미지를 만들었다고 합시다. 내 컴퓨터에만 있는 이미지를 다른 컴퓨터가 저절로 가져갈 수는 없습니다. 전달받을 곳이 필요합니다.

낯선 말 1개눌러서 뜻 보기
registry

이미지를 올려 보관하고 다른 실행 환경에서 내려받게 하는 저장소. 레지스트리라고 읽습니다.

푸드코트의 표준 가게 세트 보관소에 해당합니다. 이곳에 들어 있는 것은 영업 중인 컨테이너가 아니라 이미지입니다. 수업 자료의 Harbor는 이런 레지스트리 제품의 이름입니다.

앱 코드와 필요한 파일 → 이미지 만들기 → 레지스트리에 올리기
                                            ↓
                         실행할 컴퓨터가 이미지를 받아 컨테이너 시작

쿠버네티스는 전달받을 이미지와 실행 설정을 바탕으로 앱 실행을 관리합니다. 앱의 코드를 대신 작성하거나, 소스 파일을 알아서 이미지로 만들어 주는 것은 아닙니다.

2. 컨테이너는 Pod 안에서, Pod는 노드 위에서

쿠버네티스는 Kubernetes, 줄여서 K8s라고도 씁니다. 가운데 여덟 글자를 숫자로 줄인 같은 이름입니다. 여러 앱의 배치·개수·상태를 함께 관리하는 일을 오케스트레이션(orchestration)이라고 합니다.

낯선 말 1개눌러서 뜻 보기
cluster

쿠버네티스의 관리부와 앱을 실행하는 컴퓨터들을 묶은 하나의 운영 환경. 클러스터라고 읽습니다.

관리부는 컨트롤 플레인(control plane)이라고 합니다. 실행 요청을 받아 기록하고, 무엇이 더 필요한지 판단하는 역할입니다. 실제 앱이 일할 자리도 필요합니다.

낯선 말 1개눌러서 뜻 보기
node

클러스터에서 앱 실행을 맡는 컴퓨터. 노드라고 읽으며, 실행부를 강조해 워커 노드라고도 합니다.

실물 컴퓨터일 수도, 하나의 컴퓨터처럼 사용할 수 있게 만든 가상 컴퓨터일 수도 있습니다. 쿠버네티스는 컨테이너를 낱개로 배치하는 대신 Pod라는 단위로 묶습니다.

낯선 말 1개눌러서 뜻 보기
Pod

같은 노드에 함께 배치되는 하나 이상의 컨테이너를 묶은, 쿠버네티스의 기본 실행 단위. 파드라고 읽습니다.

왜 한 겹을 더 둘까요? 앱과 그 앱을 돕는 프로그램처럼 같은 자리에서 함께 실행되어야 하는 컨테이너를 한 단위로 다루기 위해서입니다. 같은 Pod의 컨테이너는 통신 주소인 IP를 공유하고, 앱에 연결하는 번호인 포트(port)도 같은 공간에서 사용합니다. 한 Pod에 꼭 여러 컨테이너를 넣어야 하는 것은 아닙니다.

다음은 이미 배치된 예시입니다. 각 Pod에는 주문 조회 앱 컨테이너가 하나씩 있고, 세 컨테이너는 모두 같은 이미지로 시작했습니다.

클러스터
├─ 컨트롤 플레인: 실행 요청과 배치를 관리
├─ 노드 A
│  ├─ Pod 1 ─ 주문 조회 앱 컨테이너 1
│  └─ Pod 2 ─ 주문 조회 앱 컨테이너 2
└─ 노드 B
   └─ Pod 3 ─ 주문 조회 앱 컨테이너 3

여기에는 앱 컨테이너 세 개, Pod 세 개, 실행 노드 두 개가 있습니다. 같은 이미지로 시작했다는 것과 같은 Pod·노드에 있다는 것은 별개입니다. 그림처럼 배치를 알려주지 않았다면 이미지 개수만으로 Pod나 노드 수를 알 수 없습니다.

수업 자료의 EKS는 AWS가 제공하는 관리형 쿠버네티스 서비스의 이름입니다. 서비스 이름이 달라져도 우선 볼 관계는 이 관리부·노드·Pod·컨테이너입니다.

3. “이 앱을 세 개 유지해 주세요”를 적어 전달합니다

컴퓨터마다 접속해 앱을 하나씩 켜는 대신, 쿠버네티스에는 원하는 상태를 알려줍니다. 예를 들어 “주문 조회 앱을 이 이미지로 실행하고 Pod 세 개를 유지해 주세요”라고 적는 방식입니다. 목표를 적고 시스템이 그 상태에 맞추게 하는 방식을 선언형이라고 합니다.

낯선 말 1개눌러서 뜻 보기
manifest

쿠버네티스에 만들거나 바꿀 대상의 종류·이름·설정을 적은 문서. 매니페스트라고 읽습니다.

낯선 말 1개눌러서 뜻 보기
YAML

들여쓰기와 항목 이름·값으로 데이터를 표현하는 형식. 여기서는 매니페스트를 적는 데 사용합니다.

매니페스트가 무엇을 담은 문서인지를 가리킨다면, YAML은 어떻게 적는지를 가리킵니다. 이미지 안의 구성 정보를 나타내는 “이미지 매니페스트”와도 구별합니다. 여기서는 쿠버네티스에 원하는 설정을 전달하는 문서라는 뜻입니다.

아래는 뜻을 읽기 위한 일부 발췌입니다. 실행에 필요한 항목을 생략했으므로 이대로 적용하는 파일이 아닙니다.

kind: Deployment
metadata:
  name: order-demo
spec:
  replicas: 3

kind는 대상의 종류, name은 이름입니다. Deployment는 어떤 앱 구성을 몇 개 유지할지 등을 기록하는 관리 대상입니다. 위 발췌의 replicas: 3은 같은 구성으로 실행할 Pod 복제본을 세 개 원한다는 뜻이지, 노드 세 대를 주문한 것이 아닙니다.

쿠버네티스가 등록해 관리하는 대상을 리소스(resource)라고 부릅니다. 등록된 개별 대상을 오브젝트(object)라고도 하며, Pod나 Deployment가 그 예입니다. 문서 파일과 클러스터에 등록된 오브젝트는 같지 않습니다. 내 파일만 수정했다고 원격 설정이 바로 바뀌지는 않습니다.

낯선 말 1개눌러서 뜻 보기
kubectl

내 컴퓨터에서 쿠버네티스에 조회나 변경을 요청하는 명령줄 도구.

터미널에 글자로 명령을 적는 사용 방식을 CLI라고 합니다. kubectl은 그런 도구 중 하나입니다. 두 프로그램이 요청·응답을 주고받는 약속을 API라고 하며, 쿠버네티스의 API 서버는 관리 요청을 받는 관문입니다.

내 컴퓨터의 매니페스트 → kubectl → 클러스터의 API 서버 → 관리 대상에 설정 반영

여기서 보낸 것은 “주문 조회 앱을 관리해 달라”는 요청입니다. 고객이 앱에 보내는 “내 주문을 보여 달라”는 요청과는 다릅니다. 고객의 모든 요청이 쿠버네티스 API 서버를 통과한다는 뜻은 아닙니다.

낯선 말 1개눌러서 뜻 보기
spec·status

spec은 원하는 설정, status는 시스템이 관찰해 기록한 현재 상태입니다.

설정을 받아들였다는 응답과 앱이 실제로 준비됐다는 것은 다릅니다. 목표는 세 개여도 이미지를 받거나 앱이 시작되는 동안 현재 상태는 아직 그 목표와 다를 수 있습니다.

4. 기록된 목표를 보고 관리부와 실행부가 나눠 일합니다

Deployment에 “세 개”를 적었다고 문서 자체가 컨테이너를 실행하지는 않습니다. 그 설정을 읽고 계속 일하는 프로그램이 따로 있습니다.

낯선 말 1개눌러서 뜻 보기
controller

원하는 상태와 현재 상태를 비교하고 차이를 줄이는 동작을 반복하는 관리 프로그램. 컨트롤러라고 읽습니다.

Deployment를 담당하는 컨트롤러는 그 아래 ReplicaSet이라는 관리 대상을 만들고 관리합니다. ReplicaSet에는 유지할 Pod 집합과 개수 등이 기록됩니다. ReplicaSet의 컨트롤러는 그 기록을 보고 Pod 수가 부족하면 새 Pod를 만드는 일을 맡습니다. Deployment·ReplicaSet은 관리 대상이고, 컨트롤러는 일을 하는 주체라는 차이부터 이해하면 됩니다.

새 Pod가 생겼다고 실행할 자리가 저절로 정해지는 것은 아닙니다. 다음 역할이 이어집니다.

옆으로 밀어서 비교 →
누가주문 조회 앱 예시에서 하는 일
컨트롤러목표 개수에 비해 부족한 Pod의 생성을 요청합니다.
스케줄러(scheduler)아직 자리가 없는 Pod를 어느 노드에 배치할지 정합니다.
각 노드의 kubelet자기 노드에 배정된 Pod의 컨테이너가 실행되도록 실행 도구와 협력하고 상태를 알립니다.

노드에서 컨테이너를 실제로 시작하는 실행 도구가 컨테이너 런타임이고, containerd는 그 예입니다. 지금은 이 이름들의 내부 구현보다 개수 맞추기 → 자리 정하기 → 해당 자리에서 실행하기의 역할 차이를 잡으면 됩니다. 설명을 위한 순서이며, 실제 시스템 전체가 한 번에 끝나는 단일 작업이라는 뜻은 아닙니다.

아까의 Deployment가 관리하는 Pod 하나가 삭제되었다면, 컨트롤러는 부족한 수를 채우기 위해 새 Pod를 만들 수 있습니다. 기존 Pod가 다른 노드로 걸어가거나 되살아나는 것이 아닙니다. 새 Pod는 새로 배치됩니다. 또 관리 대상에 속하지 않고 단독으로 만든 Pod까지 항상 이렇게 대체되는 것은 아닙니다.

목표를 맞춘다는 것은 status 숫자를 2에서 3으로 고쳐 쓰는 일이 아닙니다. 실제 실행 상태를 바꾸려는 것입니다. 잘못된 이미지 이름이나 부족한 컴퓨터 자원 때문에 새 앱이 실행되지 못할 수도 있으므로, 목표를 적으면 반드시 즉시 성공한다고 이해해서도 안 됩니다.

5. 켜졌다는 것과 주문을 받을 준비가 됐다는 것은 다릅니다

주문 조회 앱이 막 켜졌지만, 주문 데이터를 읽을 연결을 아직 준비 중이라고 합시다. 프로그램은 시작했어도 고객 요청에는 답하지 못할 수 있습니다.

낯선 말 1개눌러서 뜻 보기
Running·Ready

Running은 Pod의 실행 단계, Ready는 그 Pod가 요청을 받을 준비 조건을 충족했는지를 나타내는 상태입니다.

Running은 노드에 배정된 Pod의 컨테이너들이 만들어졌고, 하나 이상이 실행 중이거나 시작·재시작 중일 수 있는 단계입니다. 앱 기능이 모두 정상이라는 보증서가 아닙니다. Ready=false라면 준비 조건을 충족하지 않은 상태입니다.

쿠버네티스가 주문 기능의 정답을 스스로 아는 것은 아닙니다. 앱에 맞는 프로브(probe), 즉 상태 확인 검사를 설정해 판단을 도울 수 있습니다.

  • readiness probe는 “지금 요청을 받아도 되는가?”를 확인합니다. 설정된 기준에 따라 실패하면 준비되지 않은 것으로 표시하고, 보통 Service를 통해 새 요청을 보내는 대상에서 제외합니다. 검사 실패만으로 컨테이너를 재시작하지는 않습니다.
  • liveness probe는 “재시작이 필요한 상태인가?”를 확인합니다. 설정된 실패 기준에 도달하면 해당 컨테이너를 재시작하도록 이어질 수 있습니다. 단순히 준비가 늦다는 이유를 이 검사에 잘못 넣으면 불필요한 재시작이 생길 수 있습니다.

여기서 Service는 앱의 연결점을 제공하고 대상 Pod로 요청을 연결하는 쿠버네티스 리소스입니다. 컨테이너를 정의했던 Compose의 service 항목과는 다른 개념입니다. 연결의 자세한 설정은 다음 수업에서 다룹니다.

다음 세 상황은 따로 읽어야 합니다. 첫째·셋째 줄은 업데이트 중이 아니며 Pod 세 개를 유지하도록 관리하는 Deployment를 가정합니다.

옆으로 밀어서 비교 →
관찰한 상황구별할 일
Pod 하나가 삭제되어 두 개만 남았습니다.컨트롤러가 부족한 수를 채울 새 Pod를 만들 수 있습니다.
Pod는 그대로인데 그 안의 컨테이너가 종료됐습니다.재시작 정책에 따라 같은 Pod 안에서 컨테이너가 다시 시작할 수 있습니다. 새 Pod 생성과 다릅니다.
Pod 세 개가 그대로 존재하지만, 하나가 Running이면서 readiness 검사에 실패했습니다.준비되지 않은 Pod가 있다는 뜻입니다. 그 실패만으로 네 번째 Pod를 추가하거나 컨테이너를 재시작하는 것은 아닙니다.

Pending처럼 아직 실행 준비가 끝나지 않은 단계도 있습니다. 상태 이름만 보고 원인을 단정하지 않고, 상세 상태·발생한 사건·앱이 남긴 실행 기록을 함께 살핍니다. 수업의 get, describe, logs는 각각 이런 목록·상세 정보·앱 기록을 살펴볼 때 만날 이름입니다. 지금 명령 옵션을 외울 필요는 없습니다.

6. 내 터미널에서 쳐도 대상은 공유 클러스터일 수 있습니다

kubectl을 내 컴퓨터에서 실행한다고 내 컴퓨터의 앱만 바뀌는 것은 아닙니다. 어느 클러스터에 어떤 계정으로 연결하는지가 중요합니다.

낯선 말 1개눌러서 뜻 보기
context

kubectl이 사용할 클러스터·사용자 정보·기본 namespace를 묶은 연결 선택. 컨텍스트라고 읽습니다.

이 연결 정보는 kubeconfig라는 설정에 담깁니다. 조회를 요청하면 원격의 상태를 읽고, 변경을 요청하면 원격의 대상이 바뀔 수 있습니다. 강사의 실습 환경에서 실제로 어떤 연결을 써야 하는지는 별도 안내를 확인해야 합니다.

낯선 말 1개눌러서 뜻 보기
namespace

한 클러스터 안에서 Pod 같은 리소스의 이름과 관리 범위를 나누는 논리적 구획. 네임스페이스라고 읽습니다.

공유 클러스터의 반별 정리 구역을 떠올리면 됩니다. 같은 namespace의 같은 리소스 종류 안에서는 이름이 겹치지 않아야 합니다. 하지만 namespace만 나눴다고 통신이 자동 차단되거나 모든 권한이 분리되는 것은 아닙니다. 컨테이너 내부 격리를 설명할 때 나오는 Linux namespace와도 다른 개념입니다.

이름 외에 묶어서 고르는 방법도 있습니다.

낯선 말 1개눌러서 뜻 보기
label·selector

label은 대상에 붙이는 이름표인 키·값이고, selector는 그 이름표 등을 조건으로 대상을 고르는 규칙입니다.

다음은 같은 namespace에 있는 Pod 두 개의 읽기용 예시입니다.

옆으로 밀어서 비교 →
Pod 이름붙어 있는 label
order-demo-aapp=order-demo
order-demo-bapp=order-demo

이름은 달라도 app=order-demo라는 label 조건으로 고르면 둘 다 선택됩니다. 이름 뒤에 개인 식별자를 붙였다는 이유만으로 묶음 변경까지 안전해지지는 않습니다. label은 소유자나 접근 권한을 증명하는 표시도 아닙니다.

수업에서 변경 명령을 만나면 먼저 클러스터·계정 → namespace → 리소스 종류 → 이름 또는 선택 조건을 확인하세요. 여기서는 실제 계정이나 공유 클러스터에 접속하지 않아도, “내 명령이 누구의 무엇을 가리키는가?”를 이해하면 됩니다.

오늘의 인계 카드

오늘은 이미지가 컨테이너로 실행되고, Pod가 노드에 배치되며, 여러 관리 프로그램이 원하는 상태를 맞춘다는 관계를 만들었습니다. 이제 수업에서 새로운 이름을 만나면 실행할 내용인지, 실행 위치인지, 관리하는 역할인지부터 찾아보세요.

다음 날에는 여기서 “사용자 요청을 어떻게 연결할까?”, “앱 버전은 어떻게 교체할까?”, “설정과 남겨야 할 데이터는 어디에 둘까?”로 이어집니다. Service·Ingress는 연결, ConfigMap·Secret은 일반 설정과 민감한 설정 값, volume·PVC는 저장 공간과 그 요청을 다룰 때 만날 이름입니다. 오늘 이들의 설정법까지 알아야 하는 것은 아닙니다.
