Day 03. Tool 요청과 실제 실행 분리하기

예정 강의일 · 2026.08.20

오늘 만들 것

감자랜드 AI 고객센터에 “R-101 예약 상태를 알려 줘”라는 질문이 들어옵니다. 모델은 읽기 전용 getReservationStatus Tool 호출을 요청하고, 앱은 입력을 검사한 뒤 Repository에서 상태를 조회합니다. 조회 결과를 모델에 돌려주면 모델이 사용자에게 최종 답을 만듭니다.

왜 필요한가

모델은 DB를 직접 읽지 못하고, 모델이 Tool을 골랐다는 사실만으로 코드가 안전하게 실행되는 것도 아닙니다. 오늘은 이 문장만 기억하면 됩니다. 모델은 요청하고, 앱은 실행한다.

MCP는 여러 도구를 표준 방식으로 연결할 때 만나는 이름입니다. Agent의 반복, Memory 저장, Advisor 순서와 운영 설정은 수업에서 이어지지만, 예습에서는 읽기 전용 Tool 하나의 요청과 실행만 끝까지 따라갑니다. R-101은 흐름을 보기 위한 예시 예약 번호일 뿐 필수 선수지식이 아닙니다.

HelpDesk 전체에서는 네 요소가 서로 다른 일을 맡습니다.

상세 설명

읽기 전용 예약 상태 Tool 따라가기

아래는 요청과 실행 경계를 보여 주는 학습용 Java 조각입니다. 핵심 Tool은 조회만 하며 예약이나 변경 요청을 만들지 않습니다.

String ask(String question) {
    return chatClient.prompt()
            .user(question)
            .tools(reservationTools)
            .call()
            .content(); // Tool 결과를 받은 모델이 최종 답을 만든다
}

@Tool(description = "예약 번호로 현재 예약 상태를 조회한다")
ReservationStatus getReservationStatus(String reservationId) {
    requireValidReservationId(reservationId);
    return reservationRepository.findStatusById(reservationId).orElseThrow();
}

앱은 이 Tool을 ChatClient 호출에 연결합니다. 전체 흐름은 다음과 같습니다.

  1. 사용자가 예약 상태를 질문합니다.
  2. content()에서 모델 호출이 실행되고, 모델이 getReservationStatus 이름과 reservationId를 담은 Tool 호출을 요청합니다. 이 요청 자체가 조회 실행 결과는 아닙니다.
  3. 앱이 reservationId 형식을 검사하고 ReservationRepository 조회를 실제로 실행합니다.
  4. 앱이 ReservationStatus 결과를 모델에 전달합니다.
  5. 모델이 조회 결과를 바탕으로 사용자에게 최종 답을 만듭니다.

이 예제에서는 모델이 요청 주체이고 앱이 실행 주체입니다. Spring AI는 Tool 요청과 Java 메서드 호출, 결과 반환을 이어 주지만, 입력 검사와 Repository의 업무 규칙까지 대신 정해 주지는 않습니다.

Spring AI의 ToolContext 값은 모델에 전송되지 않고 Tool 실행에 전달됩니다. 그러나 사용자가 보낸 userId를 검사 없이 그대로 넣으면 위치만 옮겼을 뿐 안전해진 것이 아닙니다. 서버가 로그인 정보와 요청 범위에 묶어 만든 값을 전달해야 합니다.

상태를 바꾸는 Tool은 더 긴 문을 통과합니다.

모델 요청 → 형식·인가·소유자·현재 상태 검사 → 사람 승인 → 멱등성·transaction 검사 → 실행 → 결과 순서로 둡니다. CR-201 접수처럼 같은 요청이 다시 와도 중복 행이 생기지 않게 request ID와 DB 유일성 조건을 함께 검토합니다. CR-201=PENDING은 변경 요청을 접수했다는 상태이지 R-101 예약이 이미 바뀌었다는 뜻이 아닙니다. 결제·삭제·예약 변경은 승인 전에 실행하지 않습니다.

returnDirect와 기본 흐름

옆으로 밀어서 비교 →

기본 false모델에 돌아가 최종 답을 만들 때 사용입력·권한·결과 최소화·감사

returnDirect=true는 한 번의 모델 호출을 줄일 수 있지만 안전 검사를 생략하는 옵션이 아닙니다. 직접 반환할 결과가 사용자에게 보여도 되는 형태인지 앱이 책임집니다.

Memory와 Advisor

LLM 자체가 지난 대화를 영구 기억하는 것은 아닙니다. Memory는 메시지를 저장하고, Memory Advisor는 호출 때 지정한 conversation ID에 해당하는 일부 메시지를 다시 Prompt에 넣습니다. Spring AI 2.0에서는 memory advisor 호출마다 conversation ID가 필수이며 기본값이 없습니다. 서버는 이 ID를 사용자·tenant·session에 묶어 만들고, 다른 사용자의 ID를 요청값으로 그대로 받지 않아야 합니다. Advisor는 Memory뿐 아니라 RAG와 안전 처리처럼 요청·응답 앞뒤의 공통 처리를 연결하는 자리입니다.

Agent·MCP와 관찰

Agent는 모델 판단과 Tool 사용을 제한된 범위에서 반복하는 구성이고, MCP는 Tool과 자료를 연결하는 표준의 이름입니다. 반복 제어와 MCP 서버 운영은 이번 선택층에서 구현하지 않습니다. 운영에서는 Metrics·Tracing·Logging으로 호출 수, 지연, 오류와 Tool 이름을 관찰합니다. Spring AI 2.0은 Prompt와 completion 원문을 기본으로 내보내지 않습니다. Tool 인자와 결과까지 포함한 원문 로그는 개인정보·비밀을 노출할 수 있으므로 켜기 전에 마스킹과 접근 범위를 정하고, 레드팀 질문으로 우회 호출도 점검합니다.
