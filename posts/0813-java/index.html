Day 04. DI·IoC와 proxy

예정 강의일 · 2026.08.13

오늘 만들 것

Day 03에서 접수 대기 상태로 Repository 저장 경계에 전달한 예약 R-101을 확정하는 호출 경로를 준비합니다. 저장 구현은 생략했지만, 오늘은 Repository에서 조회할 수 있는 PENDING R-101이 있다고 가정합니다. 오늘은 ReservationService가 필요한 Repository를 직접 만들지 않고 받아서 쓰고, confirm("R-101") 호출 앞에는 입력 검사와 실행 기록을 붙일 수 있는 구조를 만듭니다.

감자랜드 예약의 전체 흐름
Day 03: R-101을 접수 대기 상태로 만들어 저장 경계에 전달
→ Day 04: Service와 Repository 연결 + confirm 호출의 진입 경로 확인
→ Day 05: R-101 상태와 확인 이력을 DB에 함께 확정

왜 필요한가

Service 안에서 저장 구현을 직접 new하면 메모리 저장을 DB 저장으로 바꿀 때 Service까지 고쳐야 합니다. 모든 메서드에 입력 검사와 실행 기록을 복사하면 예약 업무보다 주변 코드가 더 많아집니다. 그래서 객체를 연결하는 일과 호출 앞뒤의 반복 작업을 핵심 예약 코드에서 나눕니다.

오늘 범위는 Spring이 Repository와 Service를 준비하고, Controller 호출이 설정된 proxy를 거쳐 Service에 들어가는 구조까지입니다. 아래 Day 04 코드와 Day 05 코드는 서로 다른 두 번의 확정 요청이 아니라, 같은 confirm("R-101") 호출을 이틀에 나눠 확대해서 보는 예제입니다. 오늘은 호출이 들어가는 길을 보고, 실제 DB transaction과 결과는 Day 05에서 이어 봅니다.

지난 수업 복습

Day 03에서는 예약 요청이 Controller → Service → Repository 순서로 이동했습니다. Controller는 HTTP 요청을 받고, Service는 최소 인원 규칙을 확인하고, Repository는 PENDING 예약을 실제 저장 구현에 넘기는 경계를 맡았습니다.

낯선 말 1개눌러서 뜻 보기
의존성(Dependency)

ReservationService가 예약을 확정할 때 필요한 ReservationRepository처럼, 한 코드가 일을 하기 위해 사용하는 다른 객체.

오늘은 그 화살표 사이에서 객체가 어떻게 준비되고, Service 호출 앞뒤에 공통 기능이 어떻게 붙는지 봅니다.

오늘 수업에서 꼭 가져가야 할 것

Repository 구현을 바꾸거나 검사를 추가해도, 예약 확정 코드를 덜 고치려면 객체와 호출을 어떻게 연결해야 할까?

먼저 앱을 시작할 때와 예약 요청이 들어올 때를 나눕니다.

[앱을 시작할 때]
IoC container → Repository Bean 생성 → Service 생성자에 Repository 전달

[예약 요청이 들어올 때]
공통 기능이 설정된 경우: Controller → proxy → 실제 Service.confirm("R-101")
→ 주입받은 Repository

핵심 역할은 세 가지입니다.

  1. DI: Service가 필요한 Repository를 생성자로 받습니다.
  2. IoC: Spring이 두 객체를 만들고 연결합니다.
  3. proxy·AOP·validation: 관련 설정이 있을 때 실제 Service 호출 앞뒤에 공통 작업을 붙입니다.

아래는 Spring Boot 프로젝트 안의 연결 관계를 읽기 위한 코드 조각입니다. import, Reservation, Repository 선언과 실행 설정은 생략되어 단독 Java 파일로 실행되지는 않습니다.

생성자 안의 오른쪽 repository는 Spring에게서 받은 객체이고, 왼쪽 this.repository는 Service가 이후에도 그 객체를 사용하도록 기억해 두는 자리입니다.

@Service
@Validated
public class ReservationService {
    private final ReservationRepository repository;

    // 1. DI: Repository를 직접 new 하지 않고 생성자로 받습니다.
    public ReservationService(ReservationRepository repository) {
        this.repository = repository;
    }

    // 2. proxy가 적용할 수 있는 검증 규칙을 메서드에 표시합니다.
    public void confirm(@NotBlank String reservationId) {
        // 3. Service: 접수된 예약을 찾고 업무 동작을 실행합니다.
        Reservation reservation = repository.findById(reservationId)
                .orElseThrow();
        reservation.confirm();
    }
}

이 코드 블록에는 실제 Service만 보입니다. Method validation이나 AOP가 설정되면 Spring이 이 Service 앞에 별도의 중간 객체인 proxy를 만들어 Controller에 연결할 수 있습니다. 실행 기록도 별도 AOP 설정이 있어야 하며, @NotBlank 자체가 proxy인 것은 아닙니다.

처음에는 세 표지만 찾으면 됩니다.

  • 생성자: Service가 Repository를 밖에서 받습니다.
  • @NotBlank: 예약 번호가 비어 있지 않은지 실제 메서드 전에 검사할 수 있습니다.
  • findById → reservation.confirm(): 저장 경계에서 예약을 찾고, Service의 업무 흐름에서 상태 변경 동작을 호출합니다.

상세 설명

1. DI는 받는 코드, IoC는 준비하는 제어다

낯선 말 5개눌러서 뜻 보기
의존성 주입(DI)

Service를 만들 때 필요한 Repository를 생성자 입력으로 넣어 주는 연결 방식.

생성자 주입(Constructor Injection)

ReservationService(ReservationRepository repository)처럼 생성자의 입력값으로 필요한 객체를 받는 DI 방식.

제어의 역전(IoC)

Service가 객체를 직접 만들지 않고 Spring이 객체 생성과 연결을 맡는 것.

IoC 컨테이너(IoC Container)

Spring 안에서 빈을 만들고 필요한 생성자에 넣어 주는 부분.

빈(Bean)

Spring IoC 컨테이너가 만들어 보관하고 필요한 곳에 연결하는 객체.

같은 장면을 어느 쪽에서 보느냐에 따라 말이 달라집니다.

  • Service 쪽에서 Repository를 받는 코드가 DI입니다.
  • Spring 쪽에서 두 Bean을 만들고 연결하는 제어가 IoC입니다.

Service가 new MemoryReservationRepository()를 직접 쓰지 않으므로, Spring이 다른 Repository Bean을 연결해도 Service는 findById라는 약속을 계속 사용할 수 있습니다. 그렇다고 구현 객체가 저절로 생기는 것은 아닙니다. Spring이 찾아 만들 수 있도록 Bean으로 등록되어 있어야 합니다.

2. proxy는 실제 메서드로 가는 중간 경로다

낯선 말 3개눌러서 뜻 보기
프록시(Proxy)

관련 기능이 설정됐을 때 Controller 호출을 실제 Service보다 먼저 받아 검증·기록 같은 공통 작업을 적용할 수 있는 중간 객체.

관점 지향 프로그래밍(AOP)

여러 메서드에 반복되는 실행 기록 같은 일을 핵심 업무 코드 밖에서 호출 앞뒤에 적용하는 방식.

검증(Validation)

이 예제에서는 confirm 실행 전에 예약 번호가 비어 있지 않은지 확인하는 일.

method validation이 설정되어 있다면 Spring proxy가 @NotBlank를 보고 빈 예약 번호를 실제 confirm에 전달하기 전에 막을 수 있습니다. AOP로 실행 시간 기록을 설정했다면 같은 proxy 경로의 앞뒤에 기록을 붙일 수 있습니다.

다만 “예약이 실제로 존재하는가”, “취소된 예약을 확정해도 되는가”는 단순한 입력 검사가 아니라 예약 업무 규칙입니다. 이런 판단은 Service가 맡아야 합니다.

선택 설명 · 필요할 때 펼쳐보기

더 읽어보기: 같은 객체 안에서 직접 호출하면?

같은 객체 안에서 this.confirm()처럼 직접 호출하면 기본 Spring AOP의 proxy를 지나지 않습니다. confirm() 메서드 자체는 평범한 Java 호출로 실행되지만, proxy가 앞뒤에 붙이는 검증·기록·transaction 같은 advice는 적용되지 않을 수 있습니다. “메서드가 아예 실행되지 않는다”와 “메서드는 실행되지만 proxy 부가기능을 우회한다”를 구분해야 합니다. 이 경계는 proxy 밖에서 Service를 호출하는 오늘의 필수 흐름과 구분해 둡니다.

더 읽어보기: async는 “이미 끝났다”가 아니다

선택 용어 · 비동기(Async) — 호출한 쪽이 작업 완료를 계속 기다리지 않고 먼저 돌아갈 수 있고, 작업은 따로 실행되는 방식.

선택 용어 · TaskExecutor — Spring에서 @Async 작업의 실행을 맡을 수 있는 도구.

@Async 처리가 활성화된 앱에서 proxy를 통해 비동기 메서드를 호출하면 작업을 TaskExecutor에 맡기고 호출자는 먼저 돌아갈 수 있습니다. 먼저 돌아왔다는 사실은 작업 성공이나 완료를 뜻하지 않습니다. 실패 처리와 실행 순서는 따로 설계해야 하며, 같은 객체 내부의 직접 호출은 기본 proxy 방식에서 비동기로 가로채지지 않을 수 있습니다.

예를 들어 R-101 예약 확인 뒤 안내 알림을 비동기로 맡기면 HTTP 응답은 알림 발송 전에 돌아갈 수 있습니다. 이때 응답 성공은 “예약 확인 요청을 처리했다”는 뜻이지 “알림까지 도착했다”는 뜻이 아닙니다. executor가 받을 수 있는 작업 수, 실패 재시도와 순서, 호출한 transaction의 정보가 새 실행으로 그대로 이어지는지도 별도로 설계해야 합니다. @EnableAsync 같은 활성화와 Spring이 관리하는 proxy 경로도 필요합니다.

더 읽어보기: 설정과 반복 코드 줄이기

선택 용어 · 프로퍼티(Properties) — 서버 주소처럼 실행 환경에 따라 달라지는 값을 Java 코드 밖에 이름과 값으로 적어 두는 설정 정보.

선택 용어 · Lombok — 생성자나 값을 꺼내는 메서드처럼 반복되는 Java 코드를 자동으로 만들어 줄 수 있는 라이브러리.

application.properties에는 포트와 외부 서비스 주소 같은 설정을 둘 수 있지만, 비밀번호나 API key를 공개 저장소에 그대로 올려도 된다는 뜻은 아닙니다. 개발·테스트·운영 환경마다 값이 달라질 수 있으므로, 코드는 같은 설정 이름을 읽고 실제 값은 환경별 안전한 저장소에서 공급하는 식으로 분리합니다.

Lombok은 컴파일할 때 annotation processor가 생성자·getter 같은 Java 코드를 만들어 반복 작성을 줄입니다. 실행 중인 Spring이 빠진 메서드를 즉석에서 만드는 도구가 아닙니다. Lombok이 생성자를 만들어 줄 수는 있어도 그 생성자로 의존성을 전달하고 객체를 관리하는 주체는 Spring IoC container입니다.
