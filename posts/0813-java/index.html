지난 수업 복습

어제 예약 R-101의 요청은 Controller → Service → Repository 순서로 이동했습니다. Controller는 HTTP 요청을 받고, Service는 업무 규칙을 실행하고, Repository는 저장 경계를 맡았습니다.

오늘은 한 걸음 더 들어갑니다. ReservationService가 ReservationRepository를 사용하려면 그 객체를 어디에서 받아야 할까요?

오늘 수업에서 꼭 가져가야 할 것

ReservationService가 필요한 객체를 직접 만들지 않으면서 사용하고, 검증·기록·비동기 작업은 핵심 코드 밖에서 어떻게 붙을까?

1. DI: 필요한 객체를 밖에서 받기

@Service
public class ReservationService {
    private final ReservationRepository repository;

    // ReservationService가 직접 new 하지 않고 생성자로 받습니다.
    public ReservationService(ReservationRepository repository) {
        this.repository = repository;
    }

    public void confirm(String reservationId) {
        repository.confirm(reservationId);
    }
}

이 코드는 Spring Boot 프로젝트 안의 구조를 읽기 위한 조각입니다. import, Repository 구현과 실행 설정이 생략되어 단독 Java 파일로 실행되지는 않습니다.

낯선 말 2개눌러서 뜻 보기
DI

객체가 필요한 의존성을 직접 만들지 않고 외부에서 받는 방식.

생성자 주입

생성자의 매개변수로 필수 의존성을 받는 DI 방식.

ReservationService는 ReservationRepository를 어떻게 만드는지 알지 않아도 됩니다. 생성자로 받은 객체를 사용합니다. 그래서 테스트에서는 실제 DB Repository 대신 정해 둔 결과를 돌려주는 가짜 구현을 넣기도 쉬워집니다.

2. IoC: 만들고 연결하는 제어를 container가 맡기

낯선 말 3개눌러서 뜻 보기
IoC

객체 생성과 연결의 제어를 객체 자신이 아니라 framework 같은 외부가 맡는 관점.

IoC container

Spring에서 Bean을 만들고 필요한 의존성을 연결해 관리하는 실행 환경.

Bean

Spring IoC container가 만들고 관리하는 객체.

둘은 같은 약어가 아닙니다.

  • DI는 ReservationService 입장에서 “필요한 Repository를 밖에서 받는다”는 연결 방식입니다.
  • IoC는 Spring 입장에서 “어떤 객체를 만들고 연결할지 container가 맡는다”는 제어의 방향입니다.

이 예제에서는 IoC container가 ReservationRepository Bean을 찾고, ReservationService를 만들 때 생성자에 넣습니다.

3. proxy와 AOP: 실제 메서드 앞뒤에 공통 작업 붙이기

Controller
  → proxy
      → 입력 검증·실행 시간 기록 같은 공통 작업
      → 실제 ReservationService.confirm("R-101")
낯선 말 3개눌러서 뜻 보기
proxy

대상 객체 대신 호출을 먼저 받아 추가 작업 뒤에 실제 객체로 전달하는 대리 객체.

AOP

로깅처럼 여러 곳에 반복되는 공통 관심사를 핵심 업무 코드와 나누어 적용하는 방식.

validation

입력값이 정해 둔 조건을 만족하는지 확인하는 과정.

Spring AOP는 보통 proxy를 거친 메서드 호출에 기능을 붙입니다. 따라서 같은 객체 안에서 this.confirm()처럼 직접 부르면 proxy를 지나지 않아 AOP 기능이 적용되지 않을 수 있습니다.

Controller의 요청 DTO에 붙인 @Valid는 Spring MVC가 요청 데이터를 묶는 과정에서 검사합니다. Service의 method validation은 @Validated가 붙은 Bean을 proxy로 감싼 뒤 메서드 매개변수를 검사합니다. 둘 다 validation이지만 검사되는 위치가 다릅니다.

상세 설명

예약 R-101 확정 호출을 순서대로 읽기

  1. Spring IoC container가 ReservationRepository Bean을 만듭니다.
  2. container가 ReservationService를 만들며 Repository를 생성자로 주입합니다.
  3. Controller가 Service를 호출할 때, 설정된 기능이 있다면 proxy가 호출을 먼저 받습니다.
  4. proxy는 validation이나 기록 같은 공통 작업을 수행한 뒤 실제 confirm을 호출합니다.
  5. ReservationService는 주입받은 Repository로 R-101 확정을 요청합니다.

중요한 것은 배역 암기가 아니라 연결 방향입니다.

만들고 연결: IoC container
받아서 사용: ReservationService
호출 앞뒤 확장: proxy / AOP

더 읽어보기: async는 “이미 끝났다”가 아니다

낯선 말 2개눌러서 뜻 보기
async

호출한 작업의 완료를 그 자리에서 기다리지 않고 다른 실행 흐름에 맡길 수 있는 방식.

TaskExecutor

Spring에서 작업 실행을 맡는 추상화로, @Async 메서드의 작업을 받을 수 있다.

@Async가 적용된 메서드를 proxy를 통해 호출하면 작업을 TaskExecutor에 제출하고 호출자는 먼저 돌아갈 수 있습니다. 이것은 작업이 이미 성공했다는 뜻이 아닙니다. 실패 처리, 결과 받기와 실행 순서는 별도로 설계해야 합니다. 기본 proxy 방식에서는 같은 객체 내부의 직접 호출도 비동기로 가로채지 못할 수 있습니다.

이 설명은 @EnableAsync 등으로 비동기 Annotation 처리를 활성화한 애플리케이션을 전제로 합니다. @Async만 붙였다고 자동으로 비동기 실행이 켜지는 것은 아닙니다.

더 읽어보기: 반복 코드와 설정값 줄이기

낯선 말 2개눌러서 뜻 보기
properties

서버 포트처럼 실행 환경에 따라 달라질 수 있는 설정을 코드 밖에 적는 키-값 형식의 설정 정보.

Lombok

getter나 생성자처럼 반복되는 Java 코드를 컴파일 과정에서 생성해 주는 라이브러리.

application.properties나 application.yml에는 포트와 외부 서비스 주소 같은 설정을 둘 수 있습니다. 비밀번호와 API key를 공개 저장소에 그대로 올려도 된다는 뜻은 아닙니다.

Lombok의 @RequiredArgsConstructor는 final 필드를 받는 생성자를 만들어 줄 수 있습니다. 그러나 DI를 수행하는 주체는 Lombok이 아니라 Spring IoC container입니다. 처음에는 생성자를 직접 읽은 뒤 줄여 쓰는 편이 역할을 구분하기 쉽습니다.
