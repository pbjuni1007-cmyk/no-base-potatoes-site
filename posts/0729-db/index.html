오늘은 감자 식당 주문 처리 관제실의 두 관제 문제로 나누어 봅니다.

  1. 빠르게 찾기: 인덱스 → 실행 계획 → 측정 → 한 가지 변경 → 재측정
  2. 안전하게 함께 바꾸기: 트랜잭션 → Lock 대기 → Deadlock 판별 → 전체 재시도

한 방에서 다 해결하려다가는 감자도 계획도 같이 꼬입니다.

인덱스: 자주 찾는 주문의 위치표

테이블이 주문 기록을 모은 장부라면 인덱스는 자주 찾는 주문의 위치를 따로 정리한 위치표입니다.

인덱스가 없으면 많은 행을 차례로 확인할 수 있습니다. 알맞은 인덱스가 있으면 조건에 맞는 행의 위치부터 찾아갈 수 있습니다.

하지만 인덱스가 무조건 빠른 것은 아닙니다.

  • DB가 필요하다고 판단할 때만 사용합니다.
  • 테이블이 바뀌면 인덱스도 함께 관리해야 합니다.
  • 인덱스 자체도 저장 공간을 사용합니다.

즉, 읽기를 도울 수 있지만 쓰기와 저장에는 비용이 생깁니다.

Seq Scan·Index Scan

테이블의 행을 차례로 확인하는 방식과 인덱스를 따라 후보 행을 찾는 방식.

EXPLAIN은 조회를 시작하기 전에 예상 경로를 그려 보는 일입니다. 대상 SQL은 실행하지 않습니다.

EXPLAIN ANALYZE는 조회 경로를 실제로 실행하고 초시계로 시간과 처리량을 재는 일입니다. ANALYZE는 회의실에서 말로만 분석하지 않습니다. SQL을 진짜 실행합니다. 따라서 UPDATE나 DELETE에 사용하면 실제 데이터가 바뀔 수 있습니다.

SQL 튜닝: 감이 아니라 전후 측정

SQL 튜닝은 SQL을 짧게 줄이는 일이 아닙니다.

예상 행 수·실제 행 수

계획할 때 처리할 것으로 본 행 수와 실행 뒤 실제로 처리한 행 수.

Buffer

쿼리를 실행하며 데이터 블록을 메모리에서 찾았는지 저장 장치에서 읽었는지 보여 주는 측정 정보.

기본 흐름은 다음과 같습니다.

  1. EXPLAIN으로 예상 경로를 봅니다.
  2. EXPLAIN ANALYZE로 실제 행 수와 시간을 확인합니다.
  3. 병목으로 의심되는 한 가지를 바꿉니다.
  4. 같은 조건에서 다시 측정합니다.

Seq Scan이 보인다고 바로 실패는 아닙니다. 많은 행이 필요하다면 전체를 순서대로 읽는 편이 나을 수도 있습니다.

인덱스를 만들었다고 성능 향상도 보장되지 않습니다. 데이터 양과 값의 분포, 통계와 실행 환경이 달라지면 선택되는 계획도 달라집니다.

MVCC·Snapshot·Lock: 동시에 일할 때의 규칙

MVCC는 여러 데이터 버전을 관리해 동시에 읽고 쓰는 작업의 충돌을 줄이는 방식입니다.

Snapshot은 한 SQL이나 트랜잭션이 어떤 데이터 버전을 볼지 정한 보기 기준입니다. DB 전체를 복사한 파일은 아닙니다.

격리 수준은 동시에 실행되는 트랜잭션이 서로의 변경을 얼마나 볼지 정하는 단계입니다. 수업에서는 Read Committed, Repeatable Read, Serializable이라는 이름이 나옵니다. 이번 예습에서는 세 단계의 세부 차이보다 “보이는 데이터의 범위를 정한다”는 역할만 붙잡습니다.

PostgreSQL의 평범한 SELECT는 보통 쓰기를 막지 않습니다. 하지만 두 작업이 같은 행을 수정하려 하면 Lock이 충돌을 조정하고 한쪽이 기다릴 수 있습니다.

Deadlock은 두 작업이 서로 상대가 가진 Lock을 기다리는 순환 대기입니다. PostgreSQL은 이를 감지해 작업 하나를 취소합니다.

본문의 두 행 예제에서는 여러 행을 같은 순서로 바꾸면 순환 대기를 줄일 수 있습니다. 모든 Deadlock이 사라진다는 보장은 없으므로 트랜잭션을 짧게 유지하고, 취소된 트랜잭션 전체를 재시도해야 합니다.

상세 설명

감자 주문 조회 경로 확인하기

Day 01의 potato_shop.orders에서 고객 1번의 주문을 최신 번호부터 찾는다고 합시다. 새 문법을 더하지 않고, 같은 조회의 인덱스 전후만 비교합니다.

-- Step 1: 예상 실행 계획 확인
EXPLAIN
SELECT order_id, customer_id, menu_id, quantity
FROM potato_shop.orders
WHERE customer_id = 1
ORDER BY order_id DESC;

-- Step 2: 한 가지 후보 변경
CREATE INDEX idx_orders_customer_order
ON potato_shop.orders (customer_id, order_id DESC);

-- Step 3: 실제 실행과 측정
EXPLAIN (ANALYZE, BUFFERS)
SELECT order_id, customer_id, menu_id, quantity
FROM potato_shop.orders
WHERE customer_id = 1
ORDER BY order_id DESC;
  1. Step 1 — 예상 경로: Seq Scan, Index Scan, 예상 행 수와 Cost를 확인합니다.
  2. Step 2 — 후보 변경: 조회 조건과 정렬에 맞는 인덱스 하나를 시험합니다.
  3. Step 3 — 재측정: 같은 SQL의 실제 행 수, 실행 시간과 Buffer를 비교합니다.

플래너가 여전히 Seq Scan을 고를 수 있으므로, 계획 이름보다 같은 조건의 측정값을 비교합니다.

⚠️ EXPLAIN ANALYZE는 SQL을 실제로 실행합니다. 운영 DB나 큰 데이터에서 바로 실행하지 말고, 특히 데이터를 바꾸는 SQL은 별도의 실습 DB에서 확인하세요.

같은 주문을 동시에 수정하면

두 Session이 주문 1001번과 1002번을 반대 순서로 바꿉니다.

-- Session A: 1001 → 1002
BEGIN;
UPDATE potato_shop.orders SET quantity = quantity + 1 WHERE order_id = 1001;
UPDATE potato_shop.orders SET quantity = quantity + 1 WHERE order_id = 1002;
COMMIT;

-- Session B: 1002 → 1001
BEGIN;
UPDATE potato_shop.orders SET quantity = quantity + 1 WHERE order_id = 1002;
UPDATE potato_shop.orders SET quantity = quantity + 1 WHERE order_id = 1001;
COMMIT;

주문 처리 관제실의 작업자 A에 해당하는 Session A는 1001번 주문의 Lock을 잡은 채 1002번 Lock이 풀리기를 기다립니다. 작업자 B에 해당하는 Session B는 1002번 Lock을 잡은 채 1001번 Lock을 기다립니다. “네가 먼저 끝내.” “아니, 네가 먼저 끝내.” 이렇게 기다림이 원을 이루면 Deadlock이 될 수 있고, PostgreSQL은 이를 감지해 한쪽 트랜잭션을 취소합니다.

이 두 Session이 모두 작은 번호부터 같은 순서로 수정하면 이 예제의 순환 대기를 줄일 수 있습니다. 그래도 기다림이나 다른 Deadlock은 생길 수 있으므로 트랜잭션을 짧게 유지하고, Deadlock으로 취소되면 트랜잭션 전체를 재시도해야 합니다.

B-Tree, 복합 인덱스, 커버링 인덱스, Index Only Scan, 파티셔닝도 수업에 등장합니다. 지금은 조건과 데이터에 따라 선택하는 다음 단계의 인덱스·테이블 관리 방법이라는 이름만 알아두면 됩니다.
