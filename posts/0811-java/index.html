오늘 만들 것

감자랜드 예약 화면에 신청 세 건이 모였습니다. R-101은 4명, R-102는 0명, R-103은 2명입니다. 오늘은 인원수가 한 명 이상인 신청 번호만 모은 결과 목록 [R-101, R-103]을 만듭니다.

왜 필요한가

신청이 한 건이면 if 한 번으로 판단할 수 있습니다. 하지만 신청이 계속 들어오면 같은 조건을 건마다 다시 쓰기보다, 여러 신청을 한 목록에 담고 같은 순서로 처리하는 편이 낫습니다.

전체 예약 기능에서 오늘의 위치
R-101 한 건 판단
→ 오늘: 신청 세 건에서 접수 가능한 번호 고르기
→ 이후 수업: 선택된 신청을 웹으로 접수하고 DB에 기록

오늘 직접 만드는 범위는 Java 안에 만들어 둔 신청 목록을 처리하는 것까지입니다. 예약 화면의 버튼, 웹 요청과 데이터베이스 저장은 아직 구현하지 않습니다.

지난 수업 복습

Day 01에서는 값 하나를 변수에 담고 if로 조건을 확인했습니다. 오늘은 같은 조건을 신청 세 건에 적용하기 위해, 관련 값을 신청 한 건으로 묶고 그 묶음들을 목록에 담습니다.

Day 01의 if가 값 하나의 조건을 확인했다면, 오늘의 filter는 목록의 각 예약에 같은 조건을 적용합니다.

오늘 수업에서 꼭 가져가야 할 것

예약 신청 목록에서 인원수가 올바른 신청 번호만 고를 수 있을까?

필수 코드는 예약 신청 객체 3개 → List → stream → filter → map → toList → [R-101, R-103] 순서로 읽습니다. 먼저 객체와 목록 처리에 등장하는 일곱 단어를 실제 동작과 연결합니다.

Stream API

이 코드에서는 모든 신청을 검사하고, 통과한 신청만 번호로 바꾸어 새 목록으로 모으는 Java 기능.

코드에 들어가기 전에 객체 표현 네 가지만 연결합니다.

  • 객체: 신청 번호와 인원수처럼 관련된 값을 한 묶음으로 다루는 값
  • record RideRequest(...): 그 묶음에 id와 partySize가 있다고 정하는 코드
  • new RideRequest("R-101", 4): 실제 신청 한 건을 만드는 코드
  • request.partySize(): 그 신청에서 인원수를 꺼내 읽는 코드

작성한 Java 코드

import java.util.List;

public class Main {
    record RideRequest(String id, int partySize) {}

    public static void main(String[] args) {
        List<RideRequest> requests = List.of(
                new RideRequest("R-101", 4),
                new RideRequest("R-102", 0),
                new RideRequest("R-103", 2)
        );

        List<String> acceptedIds = requests.stream()
                .filter(request -> request.partySize() > 0)
                .map(request -> request.id())
                .toList();

        System.out.println(acceptedIds);
    }
}

콘솔 출력

[R-101, R-103]

읽을 표지는 세 개입니다.

  1. List<RideRequest> — 타입이 있는 목록: 예약 신청 객체 여러 개를 순서대로 담습니다.
  2. filter — 조건 통과: partySize()로 읽은 값이 0보다 큰 신청만 다음 단계로 보냅니다.
  3. map → toList — 번호로 바꿔 모으기: 신청을 ID로 바꾸고 새 결과 목록으로 모읍니다.

상세 설명

1. 예약 신청 객체 세 개를 List에 담기

record RideRequest(String id, int partySize)는 신청 번호와 인원수를 한 객체로 묶습니다. 그래서 R-101과 4명이 서로 떨어진 값이 아니라 하나의 예약 신청으로 움직입니다.

List.of(...)는 세 신청을 순서대로 담은 목록을 만듭니다. List<RideRequest>의 꺾쇠 안은 이 목록의 요소를 RideRequest 타입으로 다룬다는 약속입니다. Java는 코드를 실행하기 전에 목록에 다른 종류의 값이 들어가는지 확인할 수 있습니다.

제네릭은 잘못된 타입 사용을 코드를 실행하기 전에 찾도록 돕습니다. 실행 중에 모든 잘못된 값을 고치거나 예약 내용까지 검증해 주는 기능은 아닙니다.

2. filter → map → toList: 검사하고, 통과한 값만 바꾸기

requests.stream()은 목록을 원본으로 하는 처리 흐름을 준비합니다.

  1. filter(request -> request.partySize() > 0): 각 신청의 인원수가 한 명 이상인지 확인합니다.
  2. map(request -> request.id()): 통과한 신청을 예약 번호로 바꿉니다.
  3. toList(): 번호들을 새 List<String>으로 모읍니다.

R-102는 인원수가 0이라 조건을 통과하지 않아 결과가 [R-101, R-103]이 됩니다. 원본 requests 목록에서 R-102를 삭제한 것은 아닙니다.

여기서 두 람다는 각 단계가 예약 하나를 받았을 때 할 일을 적습니다. 모든 신청은 filter의 인원수 검사를 받습니다. 그 조건을 통과한 R-101과 R-103에만 map이 적용되어 신청 번호를 꺼냅니다.

3. 다음 수업에 넘길 결과 확인하기

Day 01에는 R-101 한 건의 인원수가 0보다 큰지만 판단했습니다. Day 02에는 R-101, R-102, R-103을 목록에 담고 같은 조건을 차례로 적용해, 다음 접수 단계로 넘길 번호 [R-101, R-103]을 만들었습니다.

오늘의 인계 카드
입력: R-101 · 4명, R-102 · 0명, R-103 · 2명
오늘 산출물: 접수 가능한 번호 [R-101, R-103]
다음 날 전제: R-101의 번호와 인원수 4를 웹 요청으로 보낸다

오늘 예제는 목록 처리까지만 실행합니다. Day 03에서는 선택된 번호만 보내는 것이 아니라, R-101의 번호와 인원수 4를 함께 JSON 요청에 담습니다.

더 읽어보기: Stream 코드는 언제 실제로 움직일까?

이 예제에서 filter와 map은 처리 규칙을 이어 붙이고, 마지막 toList()가 결과를 요구할 때 실제 요소 처리가 시작됩니다. 첫 회독에서는 filter → map → toList의 역할만 구분하면 충분합니다.

filter와 map은 중간 연산입니다. R-101, R-102, R-103을 지금 당장 돌기보다 “인원수가 유효한 객체만 남기고, 남은 객체에서 id를 꺼낸다”는 파이프를 만듭니다. toList() 같은 최종 연산이 결과를 요구하면 그제야 원본 요소가 파이프를 통과합니다. 그래서 중간 연산만 연결하고 최종 연산을 호출하지 않으면 원하는 목록도 만들어지지 않습니다. 이 지연 실행은 결과를 안 써도 항상 빠르다는 보장이 아니라, Stream이 필요한 처리를 묶고 최적화할 여지를 주는 동작 방식입니다.

더 읽어보기: 인터페이스와 다형성

오전 수업에는 서로 다른 구현을 같은 타입의 약속으로 다루는 방법도 나옵니다.

선택 용어 · 인터페이스(Interface) — 이 예제에서는 신청이라면 id()와 partySize()를 제공해야 한다고 정하는 Java의 공통 약속.

선택 용어 · 다형성(Polymorphism) — 서로 다른 신청 객체가 같은 인터페이스 약속을 지키면 BookingRequest라는 한 타입으로 다루는 성질.

선택 용어 · 추상화(Abstraction) — 신청을 사용하는 쪽에는 id() 같은 필요한 약속만 보여 주고, 신청 종류마다 그 일을 처리하는 자세한 코드는 따로 두는 방식.

선택 용어 · 상속(Inheritance) — extends로 기존 클래스의 값과 기능을 자식 클래스가 이어받아 사용하거나 덧붙이는 관계.

예를 들어 BookingRequest 인터페이스가 id()와 partySize()를 약속하고 RideRequest implements BookingRequest가 이를 구현하면, 목록을 List<BookingRequest>로 선언할 수 있습니다. 이때 목록은 객체 내부 구현보다 두 메서드를 호출할 수 있다는 타입 약속에 의존합니다.

클래스 상속은 extends, 인터페이스 구현은 implements로 표시합니다. 둘을 모두 “물려받기”로 뭉개지 말고, 인터페이스에서는 메서드 약속을 구현한다고 읽습니다.

이 약속에 의존하면 새로운 TourRequest가 추가돼도 목록을 처리하는 코드는 id()와 partySize()만 지키는지 확인하면 됩니다. 구현을 아무것도 몰라도 된다는 뜻은 아니고, 사용하는 쪽이 꼭 알아야 할 표면을 줄이는 선택입니다. 공통 약속이 억지로 맞지 않는 객체까지 하나의 인터페이스에 넣으면 오히려 이해하기 어려워집니다.

더 읽어보기: Annotation과 Reflection

선택 용어 · 애너테이션(Annotation) — @Override, @Service처럼 컴파일러나 Spring에 코드의 역할을 알려주는 @ 표지.

선택 용어 · 리플렉션(Reflection) — 프로그램이 실행되는 동안 클래스에 어떤 생성자·메서드·필드가 있는지 살펴보거나 사용하는 Java 기능.

Annotation은 // 주석처럼 사람에게만 남기는 메모와 다릅니다. Annotation 자체가 일을 실행하는 것도 아닙니다. @Override는 컴파일러가 상위 타입의 메서드를 제대로 재정의했는지 검사하는 데 쓰고, @Service는 Spring이 관리할 구성 요소 후보를 찾는 데 쓰입니다. 같은 @ 모양이어도 누가 언제 읽는지가 다릅니다.

Reflection은 그런 정보를 실행 중에 찾을 때 쓰일 수 있습니다. Spring이 여러 기능에서 Reflection을 활용할 수는 있지만, Spring의 모든 동작을 “Reflection이 자동으로 해 준다”로 줄일 수는 없습니다. 클래스 경로 스캔, Bean 정의와 proxy 같은 다른 장치도 함께 작동합니다. 오늘 필수 예제에서는 Reflection으로 객체를 만들거나 private 필드를 바꾸지 않습니다.
