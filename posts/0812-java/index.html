오늘 만들 것

감자랜드 예약 화면에서 R-101을 4명으로 신청했습니다. 오늘은 이 JSON 요청을 Java 객체로 받고, 최소 규칙을 확인한 뒤 **접수 대기 상태(PENDING)**인 예약을 Repository 저장 경계에 넘기는 흐름을 만듭니다.

왜 필요한가

이 예제의 온라인 예약 기능은 화면이 보낸 JSON을 ReservationRequest로 바꾼 뒤, 예약할 수 있는 값인지 판단하고 보관할 대상을 만들어 Repository에 맡깁니다. 역할을 나누면 요청 형식, 예약 규칙, 저장 방식이 바뀔 때 고칠 위치를 찾기 쉬워집니다.

전체 예약 기능에서 오늘의 위치
Java 안에서 고른 R-101
→ 오늘: JSON 요청을 받아 PENDING 예약을 저장 경계까지 전달
→ 이후 수업: 객체를 연결하고 DB에 확정

오늘 코드에는 Repository의 save 약속까지만 있습니다. 실제 메모리 저장 코드도, 데이터베이스(DB)·JPA 저장 코드도 구현하지 않습니다.

POST /reservations HTTP/1.1
Content-Type: application/json

  "id": "R-101",

HTTP

예약 화면과 서버가 요청과 결과를 주고받을 때 따르는 웹 메시지 규칙.

POST

이 요청에서는 서버에 새 예약을 접수해 달라는 뜻을 나타내는 HTTP 방식.

요청 본문(Request Body)

HTTP 요청에서 예약 번호와 인원수처럼 서버에 보낼 실제 내용을 담는 부분.

JSON

id와 partySize처럼 이름과 값을 짝지어 글자로 전달하는 데이터 형식.

아래는 Spring Boot 프로젝트의 여러 파일에서 호출 흐름만 뽑아 모은 학습용 코드 조각입니다. Controller 메서드는 생략된 @RestController—요청을 받고 반환값을 웹 응답으로 보내는 Controller 표시—클래스 안에 있다고 가정합니다. import, package, class의 필드·생성자, 실행 설정과 오류 응답 처리는 생략했습니다. 하나의 .java 파일로 그대로 실행하는 예제는 아닙니다.

첫 회독에는 다음 네 줄만 순서대로 찾습니다. 나머지 선언과 응답 조립 코드는 네 줄이 어떻게 연결되는지 확인할 때만 보면 됩니다.

  1. @RequestBody ReservationRequest request — JSON에서 바뀐 Java 객체 받기
  2. reservationService.create(request) — 예약 규칙을 확인할 Service 호출하기
  3. new Reservation(..., "PENDING") — 아직 확정되지 않은 예약 만들기
  4. reservationRepository.save(pending) — Repository 저장 경계에 맡기기
// 0. HTTP 요청과 응답에 사용할 Java 값
public record ReservationRequest(String id, int partySize) {}
public record ReservationResponse(String id, int partySize, String status) {}
public record Reservation(String id, int partySize, String status) {}

// 1. Controller 메서드: JSON 요청을 Java 객체로 받아 Service에 전달
@PostMapping("/reservations")
public ReservationResponse create(
        @RequestBody ReservationRequest request) {
    return reservationService.create(request);
}

// 2. Service 메서드: 최소 규칙을 확인하고 PENDING 예약 생성
public ReservationResponse create(ReservationRequest request) {
    if (request.partySize() <= 0) {
        throw new IllegalArgumentException("예약 인원은 1명 이상이어야 합니다.");
    }

    Reservation pending = new Reservation(
            request.id(), request.partySize(), "PENDING");
    Reservation saved = reservationRepository.save(pending);

    return new ReservationResponse(
            saved.id(), saved.partySize(), saved.status());
}

// 3. Repository: 저장을 맡길 수 있다는 약속만 선언
public interface ReservationRepository {
    Reservation save(Reservation reservation);
}

Repository 인터페이스는 save라는 약속만 보여 줍니다. 이 코드만으로는 메모리나 DB 어디에도 실제로 저장되지 않습니다.

throw new IllegalArgumentException(...)은 인원수가 0 이하일 때 정상 예약 흐름을 멈추고, 잘못된 값이 들어왔음을 알리는 코드입니다. 오늘은 예외 문법을 외우지 않고 잘못된 신청은 Repository까지 보내지 않는다는 흐름만 봅니다.

상세 설명

1. JSON 표현과 Java 객체는 서로 다르다

같은 예약을 말해도 위치에 따라 형태가 다릅니다.

  • 웹의 예약 대상: /reservations라는 주소로 구별하는 예약들
  • JSON 표현: 네트워크로 전달한 {"id":"R-101","partySize":4}라는 글자
  • Java 객체: Controller와 Service가 JVM 안에서 다루는 값

/reservations가 Java 객체인 것도 아니고, JSON 글자가 Java 객체인 것도 아닙니다. 서로 연결되지만 같은 것은 아닙니다.

2. Spring MVC는 JSON을 Controller 입력값으로 연결한다

낯선 말 3개눌러서 뜻 보기
Spring MVC

HTTP 주소와 방식을 보고 실행할 Controller 메서드를 찾고 요청·응답 변환을 돕는 Spring 기능.

애너테이션(Annotation)

@PostMapping, @RequestBody처럼 Spring이 읽을 코드 역할을 표시하는 @ 표지.

컨트롤러(Controller)

Spring이 JSON에서 만든 ReservationRequest를 받아 Service를 호출하는 요청 입구.

Spring MVC는 POST /reservations에 맞는 Controller 메서드를 찾습니다. @RequestBody 표지를 보고 JSON 요청 본문을 ReservationRequest로 바꿔 매개변수에 넣습니다.

Annotation은 Spring이 읽는 표지입니다. @PostMapping이나 @RequestBody 자체가 예약 규칙을 판단하거나 저장을 실행하지는 않습니다.

3. Service는 업무 규칙을 확인하고 PENDING 예약을 만든다

낯선 말 1개눌러서 뜻 보기
서비스(Service)

예약 인원이 규칙에 맞는지 판단하고 저장할 예약을 만드는 코드.

Service의 partySize > 0 검사는 조건문 흐름을 보기 위한 최소 규칙입니다. 실제 예약 서비스라면 최대 정원, 날짜, 중복 예약 등 더 많은 규칙이 필요할 수 있습니다.

규칙을 통과한 R-101은 PENDING 상태로 만들어집니다. 이는 “접수는 됐지만 아직 확정되지 않음”이라는 뜻입니다. Day 03에서는 CONFIRMED로 만들지 않습니다.

4. Repository는 저장 방식 앞의 경계다

낯선 말 1개눌러서 뜻 보기
리포지토리(Repository)

Service가 저장할 예약을 건네고 저장 결과를 받아오는 통로. 실제 저장 방법은 뒤의 구현이 맡습니다.

ReservationRepository에는 save 메서드의 이름, 입력과 결과만 있습니다. 그 뒤에서 메모리를 쓸지, DB와 JPA를 쓸지는 아직 정하지 않았습니다. 따라서 이 글에서 말할 수 있는 것은 Repository에 저장을 맡겼다는 것까지입니다. 실제로 보관됐다고 주장할 수는 없습니다.

save가 돌려준 예약으로 만든 ReservationResponse는 Controller로 돌아갑니다. 이 메서드가 들어 있다고 가정한 @RestController는 반환값을 HTTP 응답 본문으로 보내라는 의미도 포함하므로, Spring MVC가 응답 객체를 JSON 같은 전송용 표현으로 바꿔 사용자 화면 쪽으로 보낼 수 있습니다.

선택 설명: 왜 세 역할로 나눌까?

한 메서드에서 요청을 받고, 인원수를 검사하고, 저장 방식까지 모두 처리할 수도 있습니다. 하지만 요청 형식, 예약 규칙, 저장 기술은 서로 다른 이유로 바뀝니다. Controller, Service, Repository로 나누면 무엇이 바뀌었을 때 어느 코드를 살펴봐야 하는지 찾기 쉬워집니다.

옆으로 밀어서 비교 →
바뀐 요구먼저 살펴볼 역할이유
요청 JSON의 필드 이름이 partySize에서 guestCount로 바뀜Controller와 요청 DTO바깥 요청을 Java 입력으로 바꾸는 경계이기 때문
예약 가능 인원이 최대 8명으로 바뀜Service저장 기술과 무관한 업무 규칙이기 때문
메모리 저장을 PostgreSQL로 바꿈Repository 구현Service가 저장 방식의 세부를 직접 알지 않게 하기 때문

실제 변경은 한 파일에만 끝나지 않을 수 있습니다. DTO 필드가 바뀌면 테스트와 API 문서도 함께 바뀔 수 있고, DB 변경이 업무 규칙에 영향을 줄 수도 있습니다. 표는 “변경 이유의 주된 소유자가 어디인가”를 찾는 출발점이지 절대적인 벽이 아닙니다.

이 구분이 모든 프로젝트의 유일한 정답은 아닙니다. 오늘은 Spring 수업에서 요청의 이동 경로를 읽기 위한 기본 구조로 사용합니다.
