오늘 만들 것

Day 1에서 계획한 수강신청을 강의·수강신청 업무로 나눕니다. 나뉜 서비스가 강의를 확인하고 신청을 저장한 뒤, 완료 사실을 알림과 추천 기능에 전하는 흐름까지 연결합니다.

왜 필요한가

서비스를 나누면 한 부분을 따로 바꾸고 배포하기 쉬워질 수 있습니다. 대신 프로그램 안의 함수 호출이 네트워크 통신으로 바뀌고 각 서비스의 데이터가 서로 다른 시점에 바뀔 수 있습니다. MSA는 작은 상자를 많이 그리는 기술이 아니라 이 이득과 비용을 감당할 경계를 정하는 일입니다.

지난 수업 복습

Day 1의 기획 회의실에서는 다음 인계물을 만들었습니다.

User Story US-ENR-01 — 수강생으로서 원하는 강의를 신청하고 결과를 확인하고 싶다.

Acceptance Criteria — 존재하는 강의만 신청할 수 있고, 같은 강의를 중복 신청하지 않으며, 성공하면 신청 결과를 확인할 수 있다.

Sprint Goal — 수강생이 같은 강의를 중복 신청하지 않고 신청 결과를 확인한다.

Task는 강의 확인, 수강신청 저장, 완료 사실 알리기로 나눴습니다. 아직 기능을 구현하거나 Review한 것은 아닙니다. 오늘 이 계획을 실제 동작으로 바꿉니다.

Java·Spring 수업에서는 하나의 앱 안에서 request → Controller → Service → Repository → DB로 요청이 흘렀습니다. 서비스를 나누면 이 중 일부 연결이 같은 앱의 method 호출이 아니라 네트워크 request·response가 됩니다. REST API는 그때 프로그램끼리 요청과 응답을 주고받기 위한 계약과 입구입니다.

오늘 수업에서 꼭 가져가야 할 것

하나의 앱을 어디서 나누고, 나뉜 서비스는 어떻게 다시 연결할까?

1. MSA는 무조건 정답이 아니라 trade-off다

trade-off는 한 이득을 얻는 대신 다른 비용이나 제약도 함께 받아들이는 선택입니다.

Monolith는 여러 기능을 주로 하나의 배포 단위로 운영하는 구조입니다. **MSA(Microservice Architecture)**는 업무별 서비스를 독립적으로 바꾸고 배포할 수 있게 나눈 구조입니다.

작고 단순한 앱이라면 내부 기능을 잘 나눈 Monolith가 이해하기도 운영하기도 더 쉽습니다. MSA는 특정 업무가 서로 다른 속도로 바뀌거나 따로 확장·배포해야 할 필요가 있을 때 검토합니다. 이런 분리 필요가 여러 서비스의 네트워크 협력 비용보다 커야 합니다. 서비스를 많이 나눴다는 사실만으로 성능이나 개발 속도가 좋아지지는 않습니다.

2. 업무 경계와 데이터 소유권을 함께 정한다

프로그램이 해결하는 업무 영역인 domain을 기준으로 수강신청 운영동을 다음처럼 나눠 봅니다.

옆으로 밀어서 비교 →
서비스 후보책임지는 업무소유하는 데이터
Course Service신청 가능한 강의 확인강의 정보
Enrollment Service수강신청 생성·중복 방지수강신청 정보
Notification Service완료 알림 처리알림 처리 상태

Microservice는 코드가 작은 클래스나 물리 서버 한 대가 아닙니다. 한 업무 능력과 그 업무의 데이터 변경 규칙을 책임지고 다른 부분과 독립적으로 바뀔 이유가 있는 서비스입니다.

각 서비스는 자기 장부를 책임집니다. Enrollment Service가 Course Service의 DB table을 직접 읽으면 Course Service의 규칙을 우회하게 됩니다. 필요한 결과는 API나 event처럼 합의한 계약을 통해 받습니다.

3. Gateway와 Service Discovery는 다른 문제를 푼다

API Gateway는 외부 request를 받는 공통 입구입니다. URL 같은 정보를 보고 알맞은 서비스로 보낼 수 있지만 모든 업무 규칙을 넣는 창고나 인증 서버 자체는 아닙니다.

Service Discovery는 지금 실행 중인 서비스의 위치를 등록하고 찾는 기능입니다. 교안에서는 Eureka가 이 역할을 맡습니다. 위치를 알려 줄 뿐 request를 대신 전달하거나 수강신청 업무를 처리하지 않습니다.

4. 답을 기다리는가부터 통신 방식을 고른다

Enrollment Service는 강의가 있는지 확인한 뒤에만 신청을 저장할 수 있습니다. 이 예제에서는 Course Service에 동기 REST request를 보내고 response를 기다립니다.

신청 저장이 끝난 뒤의 알림과 추천 갱신은 다릅니다. Enrollment Service가 두 후속 작업의 완료까지 기다릴 필요가 없다면 CourseApplied event를 course-applied Kafka Topic에 발행할 수 있습니다. 다른 서비스는 필요한 때 그 event를 소비합니다.

REST가 모든 동기 통신의 유일한 방법이거나 Kafka가 모든 비동기 통신의 유일한 방법이라는 뜻은 아닙니다. 먼저 호출자가 다음 단계 전에 결과를 기다려야 하는지 판단합니다. 이 강의에서는 각각 REST와 Kafka로 구현합니다.

상세 설명

US-ENR-01을 서비스 흐름으로 실행한다

Step 1. 외부 수강신청 request를 받는다

수강생의 request가 API Gateway에 들어옵니다. Gateway는 Enrollment Service로 routing합니다. 실행 위치가 바뀔 수 있다면 Service Discovery에서 현재 service instance의 위치를 찾습니다.

Step 2. 신청 전에 강의를 확인한다

Enrollment Service는 Course Service에 강의 확인 request를 보냅니다. 이 답이 없으면 신청 저장을 진행할 수 없으므로 response를 기다립니다.

네트워크 request는 같은 프로그램 안의 함수 호출보다 실패 지점이 많습니다. 시간 제한과 실패 응답을 정해야 하며, Course Service가 응답하지 않았는데 신청을 성공으로 저장해서는 안 됩니다.

Step 3. 자기 데이터에 수강신청을 저장한다

강의가 있고 중복 신청이 아니라면 Enrollment Service가 자기 DB에 ENR-101을 저장합니다. Course Service나 Notification Service가 이 table을 직접 바꾸지 않습니다.

낯선 말 1개눌러서 뜻 보기
data consistency

여러 데이터가 함께 지켜야 할 규칙과 현재 상태가 서로 모순되지 않는 성질.

서비스를 나누면 하나의 DB transaction으로 모든 동작을 함께 성공하거나 실패하게 묶기 어렵습니다. 어떤 서비스가 어떤 데이터를 최종 책임지는지 먼저 정해야 합니다.

Step 4. 완료 사실을 event로 발행한다

저장이 성공하면 Enrollment Service가 다음처럼 최소한의 event payload를 발행합니다.

{
  "type": "CourseApplied",
  "enrollmentId": "ENR-101"
}

Notification Service와 Recommend Service는 이 event를 각자 처리할 수 있습니다. event를 받아 처리하는 서비스 하나가 잠시 실패해도 Enrollment Service가 이미 끝낸 저장을 다시 되돌릴 필요는 없습니다. 다만 재처리 과정에서 같은 event가 다시 전달될 수 있으므로 중복에 안전해야 합니다.

낯선 말 1개눌러서 뜻 보기
duplicate

같은 작업을 다시 시도하는 과정 등으로 같은 request나 event가 둘 이상 처리될 수 있는 상황.

Kafka를 썼다고 event가 즉시 처리되거나 전체 순서가 보장되는 것은 아닙니다. 업무 결과의 end-to-end 정확히 한 번 처리도 자동으로 완성되지 않습니다.

DB 저장과 event 발행도 별개의 동작이라 저장은 성공했지만 발행은 실패할 수 있습니다. 실제 시스템은 발행할 event를 데이터와 함께 기록하고 별도 작업이 다시 보내는 방식 등으로 이 틈을 보완합니다. 이번 예습에서는 그 구현까지 다루지 않지만, 두 동작이 자동으로 한 묶음이 되지는 않는다는 경계는 기억합니다.

Step 5. 기능을 확인하고 Sprint를 닫는다

**Definition of Done(DoD)**은 Increment가 완료됐다고 팀이 공통으로 인정할 품질 기준입니다.

Definition of Done을 만족하며 실제로 신청할 수 있는 전체 기능이 Increment입니다. Increment는 ENR-101 데이터와 CourseApplied event를 만들어 내는 사용 가능한 기능이고 두 값은 그 기능이 동작했음을 보여 주는 업무 결과이자 확인 증거입니다.

Sprint Review에서는 이 결과와 현재 상황을 함께 보고 다음 Product Backlog를 조정합니다. Sprint Retrospective에서는 제품 기능이 아니라 팀의 협업·과정·도구를 돌아보고 다음 개선을 고릅니다.

OIDCOAuth 2.0 위에서 로그인한 사용자의 신원을 어떻게 전달할까모든 access token이 JWT라는 규칙
JWT사용자나 권한 같은 정보를 token 문자열로 어떻게 표현할까token의 자동 폐기·인가 성공

OAuth 2.0은 권한 위임의 틀이고, 로그인 신원 정보는 OIDC가 보완합니다. JWT는 사용할 수 있는 token 형식 중 하나일 뿐 OAuth access token이 언제나 JWT인 것은 아닙니다. JWT는 서명·MAC 또는 암호화해서 보호할 수 있으며, 어떤 보호도 없이 만든 JWT도 규격상 존재하므로 검증하지 않은 내용을 신뢰해서는 안 됩니다. Gateway가 공통 검사를 도울 수 있어도 각 서비스의 업무 인가 규칙까지 모두 대신하지는 않습니다.

선택 설명 · retry와 duplicate를 함께 설계하기

선택 용어 · retry — 실패한 동작을 조건과 횟수를 정해 다시 시도하는 것.

선택 용어 · idempotency — 같은 요청을 반복해도 최종 업무 결과가 한 번 처리한 것과 같게 만드는 성질.

네트워크가 잠시 끊기면 같은 request나 event를 다시 시도할 수 있습니다. 그러나 첫 처리는 성공했고 응답만 사라졌다면 retry가 같은 업무를 두 번 만들 수 있습니다.

옆으로 밀어서 비교 →
상황확인할 것
retry일시 실패인지, 몇 번·어떤 간격으로 다시 시도할지
duplicate같은 업무 ID가 이미 처리됐는지
idempotency같은 입력을 반복 처리해도 최종 결과가 한 번 처리한 것과 같은지

예를 들어 ENR-101 또는 별도의 업무 요청 ID에 같은 값을 두 번 저장하지 못하게 하는 DB 중복 방지 규칙을 두고 이미 처리된 event를 기록할 수 있습니다. Kafka의 exactly-once 관련 기능이 있더라도 DB와 외부 API, 사용자에게 보이는 결과까지 자동으로 한 번만 발생하는 것은 아닙니다.

선택 설명 · 다른 서비스 데이터가 필요할 때

선택 용어 · read model — 여러 원본의 정보를 읽기 편한 모양으로 미리 조합해 둔 조회용 데이터.

옆으로 밀어서 비교 →
접근적합한 상황주의점
API지금 최신 답이 필요하고 상대 서비스 응답을 기다릴 수 있음지연·부분 장애가 호출 흐름에 전달됨
event변경 사실을 받아 자기 조회 데이터를 갱신해도 됨지연·순서·중복을 다뤄야 함
read model여러 서비스의 정보를 조회용으로 미리 조합함원본과 갱신 시점이 다를 수 있음
다른 서비스 DB 직접 접근당장은 빠르게 구현해 보임소유 서비스의 규칙을 우회하고 DB 구조에 강하게 결합됨

한 서비스 내부에서 자기 DB table의 관련 데이터를 합쳐 읽는 것은 가능합니다. 문제가 되는 것은 다른 서비스가 소유한 DB를 직접 읽거나 바꿔 업무 경계를 깨는 방식입니다.
