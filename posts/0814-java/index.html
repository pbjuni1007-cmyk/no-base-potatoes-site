오늘 만들 것

DB에 접수 대기 상태로 보관돼 있다고 가정한 예약 R-101을 확정합니다. 예약 상태는 CONFIRMED로 바꾸고, reservation_history에는 “어느 예약이 어떤 상태로 바뀌었는지” 확인 이력을 한 건 남깁니다.

감자랜드 예약의 마지막 저장 흐름
PENDING R-101 조회
→ Reservation 객체 상태를 CONFIRMED로 변경
→ 확인 이력 추가
→ 성공하면 두 DB 변경 모두 확정
→ 둘 중 하나가 실패해 transaction이 취소되면 둘 다 확정하지 않음

왜 필요한가

Java 객체의 값만 바꾸면 서버를 다시 시작한 뒤 결과가 남지 않습니다. 예약 상태만 바뀌고 이력 저장이 실패하면 앞뒤가 맞지 않는 데이터도 생깁니다. 그래서 Java 객체와 DB 기록을 연결하고, 두 변경을 하나의 성공·실패 단위로 묶어야 합니다.

Day 03의 코드는 Repository 저장 경계까지만 보여 줬습니다. 오늘은 그 뒤에 JPA 구현이 연결되어 R-101의 PENDING row가 DB에 이미 있다고 가정합니다. Day 03의 학습용 Reservation record를 그대로 entity로 쓰는 것이 아니라, 별도 JPA entity class로 연결하거나 모델을 교체하는 과정이 생략됐다고 봅니다. 아래 코드는 Spring Boot와 JPA 프로젝트의 여러 파일에서 핵심 선언을 한 블록에 모은 학습용 조각입니다. import, Repository 선언과 설정이 생략되어 단독 Java 파일로 실행되지는 않습니다.

리포지토리(Repository)

Service가 DB 저장 방법의 세부 구현을 직접 알지 않아도 예약 조회와 저장을 맡길 수 있는 코드 경계.

기본 키(Primary Key)

R-101처럼 한 테이블 안에서 각 예약 기록을 하나씩 구별하는 값.

하지만 repository.findById(...)와 save(...)라는 이름만으로는 Java 객체가 DB에 언제 반영되고, 두 변경이 언제 함께 성공하는지 알 수 없습니다. 오늘은 Repository 뒤의 JPA와 transaction을 펼쳐 봅니다.

오늘 수업에서 꼭 가져가야 할 것

예약 상태와 확인 이력 중 하나를 저장하지 못하면 DB에는 무엇이 남아야 할까?

아래 코드 한 블록에서 다섯 표지만 찾습니다.

  1. @Entity와 @Id: Java 객체를 어떤 DB 기록과 연결할지 표시합니다.
  2. @Transactional: 두 DB 변경의 성공·실패 경계를 엽니다.
  3. findById: 기존 PENDING 예약을 조회합니다.
  4. reservation.confirm(): 관리 중인 Java 객체의 상태를 바꿉니다.
  5. historyRepository.save(...): 같은 작업 안에 확인 이력을 추가합니다.
@Entity
@Table(name = "reservations")
public class Reservation {
    @Id
    private String id;

    private String status;

    protected Reservation() {} // JPA가 객체를 만들 때 쓰는 빈 생성자. 오늘은 읽지 않습니다.

    public void confirm() {
        this.status = "CONFIRMED";
    }
}

@Service
public class ReservationService {
    private final ReservationRepository reservationRepository;
    private final ReservationHistoryRepository historyRepository;

    public ReservationService(
            ReservationRepository reservationRepository,
            ReservationHistoryRepository historyRepository
    ) {
        this.reservationRepository = reservationRepository;
        this.historyRepository = historyRepository;
    }

    @Transactional
    public void confirm(String reservationId) {
        Reservation reservation = reservationRepository
                .findById(reservationId)
                .orElseThrow();

        reservation.confirm();
        historyRepository.save(
                new ReservationHistory(reservationId, "CONFIRMED")
        );
    }
}

ORM

테이블(Table)

Reservation.status와 DB의 상태 칸처럼 Java 값과 DB 칸의 짝을 정하는 일.

이 코드에 UPDATE SQL이 직접 보이지 않아도 JPA가 관리 중인 entity의 변화를 찾아 SQL로 반영할 수 있습니다. 다만 Java 객체의 필드가 바뀐 순간과 DB transaction이 성공한 순간은 같지 않습니다.

상세 설명

1. entity와 row는 연결되지만 같은 물건은 아니다

Reservation entity는 실행 중인 JVM 안의 Java 객체이고, reservations table의 row는 DB에 남은 기록입니다. JPA의 mapping이 둘의 대응을 관리합니다.

Java에서 보는 값                 DB에 남는 기록
Reservation.id = "R-101"   ↔    reservations의 id 칸
Reservation.status          ↔    reservations의 status 칸

@Entity는 이 클래스가 JPA 관리 대상임을, @Table은 연결할 table 이름을, @Id는 entity를 구별하는 값을 표시합니다. Annotation만 붙였다고 모든 저장 설정과 table이 자동으로 올바르게 준비되는 것은 아닙니다.

2. JPA는 조회한 entity의 변화를 추적할 수 있다

transaction 안에서 JPA가 조회해 관리하는 R-101 entity라면, reservation.confirm() 뒤 처음 상태와 달라졌음을 찾아 SQL로 반영할 수 있습니다. 이를 흔히 변경 감지라고 합니다. 그래서 코드에 reservationRepository.save(reservation)가 다시 보이지 않아도 변경이 DB로 전달될 수 있습니다.

3. transaction은 두 변경의 성공·실패 경계다

낯선 말 3개눌러서 뜻 보기
트랜잭션(Transaction)

예약 상태 변경과 이력 저장을 함께 성공시키거나 함께 취소하도록 묶는 DB 작업 단위.

커밋(Commit)

트랜잭션 안의 변경을 성공 결과로 DB에 확정하는 일.

롤백(Rollback)

트랜잭션 안에서 시도한 DB 변경을 성공 결과로 확정하지 않는 일.

Spring proxy가 @Transactional confirm(...) 호출을 처리하면 transaction을 시작합니다. 메서드 본문이 정상 종료되면 Spring proxy가 commit을 시도합니다. JPA가 필요한 SQL을 보내고 DB commit까지 성공해야 예약 상태와 이력이 함께 확정됩니다. 그 과정에서 transaction이 취소되면 두 DB 변경은 모두 확정되지 않고, DB의 R-101은 기존 PENDING 상태를 유지합니다.

입력: DB에 있다고 가정한 PENDING R-101
오늘 산출물: CONFIRMED 상태와 확인 이력을 한 transaction으로 처리

Java 문법에서 시작한 예약 하나가 목록 처리, 웹 요청, 객체 연결을 지나 DB 기록으로 남는 길이 이어졌습니다. 같은 R-101을 따라왔지만 Java 객체, JSON 표현, REST 자원, JPA entity와 DB row는 각 단계의 서로 다른 표현입니다.

선택 설명 · 필요할 때 펼쳐보기

더 읽어보기: flush와 예외·동시성의 경계

선택 용어 · EntityManager — 엔티티를 조회·저장하고 값의 변화를 관리하는 JPA 도구.

선택 용어 · 영속성 컨텍스트(Persistence Context) — 조회한 엔티티와 그 변화를 JPA가 기억하는 관리 공간.

선택 용어 · 플러시(Flush) — JPA가 기억한 변경을 SQL로 DB에 보내 맞추는 과정. 성공을 확정하는 commit과는 다릅니다.

find로 R-101 entity를 조회하면 transaction 안에서 관리 대상이 됩니다. 그 객체의 상태를 CONFIRMED로 바꾸면 JPA가 처음 값과 현재 값을 비교하고, flush 시점에 필요한 UPDATE SQL을 DB로 보냅니다. commit이 성공해야 transaction의 변경이 확정되고, 중간에 rollback되면 같은 transaction의 DB 변경은 취소됩니다.

flush 뒤에도 transaction이 rollback되면 같은 transaction의 DB 변경은 확정되지 않습니다. Rollback은 DB 결과를 취소하는 규칙이며, 이미 바뀐 Java 객체의 필드까지 자동으로 원래 값으로 되돌린다는 뜻은 아닙니다. Spring의 기본 설정에서는 @Transactional 메서드 밖으로 나간 RuntimeException이나 Error가 rollback 대상입니다. Checked exception을 쓰거나 예외를 메서드 안에서 잡으면 기본 규칙이 달라질 수 있습니다.

Transaction은 두 변경을 한 성공·실패 단위로 묶지만, 동시에 들어온 요청이 같은 예약을 바꾸는 문제를 자동으로 막지는 않습니다. 그런 문제에는 DB 제약, lock이나 재시도 같은 별도 설계가 필요할 수 있습니다.

더 읽어보기: save와 새 entity 판단

Spring Data JPA의 JpaRepository는 자주 쓰는 저장·조회 기능을 제공합니다. 새 entity로 판단하면 내부적으로 EntityManager.persist, 기존 entity로 판단하면 EntityManager.merge를 사용할 수 있습니다.

기본 판정은 무조건 “ID가 있으면 기존 entity”가 아닙니다. primitive가 아닌 @Version 속성이 있으면 먼저 그 값이 null인지 보고, 그런 version 속성이 없을 때 ID가 null인지 확인합니다. 따라서 직접 ID를 미리 부여하면서 version도 쓰지 않는 설계에서는 새 객체인데 기존 entity로 판정될 수 있고, 이때 Persistable.isNew() 같은 별도 전략을 검토합니다. 오늘 필수 흐름은 이미 조회해 관리 중인 entity의 변경 추적이므로 save()의 신규 판정을 거치는 장면과 구분합니다.

OpenAPI는 API 계약의 표현이고 Swagger UI는 그것을 보여 주는 화면입니다. Actuator의 /actuator/health와 metrics는 실행 중인 애플리케이션을 관찰하는 정보입니다. 셋 모두 JPA 저장 기능은 아닙니다. /actuator/metrics는 기본 설정에서 웹에 노출되지 않으며, 민감한 endpoint를 전부 외부에 공개해서도 안 됩니다. Actuator가 감자랜드 놀이기구의 물리 안전을 검사하는 장치인 것도 아닙니다.
