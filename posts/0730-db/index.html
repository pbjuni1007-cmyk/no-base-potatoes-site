반복 작업을 DB에 맡길 때 어디까지 자동화하고, Cloud DB에서도 우리가 직접 책임져야 할 것은 무엇일까요?

오늘은 두 경계를 우선 붙잡습니다. Trigger 실패는 원래 데이터 변경에도 영향을 줄 수 있고, DBaaS를 써도 스키마·쿼리·권한·복구 책임이 사라지지 않습니다. 나머지 운영 용어는 서로 어떤 문제를 다루는지만 연결합니다.

Function·Procedure·Trigger: 계산 기능, 승인된 처리 절차, 자동 감지 규칙

이 글에서는 가장 단순한 역할부터 이렇게 구분합니다.

  • Function은 입력을 받아 계산한 값을 돌려주는 계산 기능입니다.
  • Stored Procedure는 여러 SQL과 제어 흐름을 하나로 묶어 호출하는 승인된 처리 절차입니다.
  • Trigger는 지정한 데이터 변경을 감지해 실행되는 자동 감지 규칙입니다.

감사 로그

누가 언제 무엇을 바꿨는지 나중에 확인할 수 있도록 남긴 기록.

감자 식당 운영 본부에서 Function은 계산 기능, Procedure는 처리 절차, Trigger는 지정한 시점에 실행되는 자동 규칙입니다. 이 글의 AFTER INSERT 예제에서는 주문 데이터가 추가된 뒤 Trigger가 실행됩니다. 실행 시점은 Trigger를 만들 때 BEFORE, AFTER 같은 옵션으로 정합니다.

여기서 ‘승인된’은 식당에서 미리 정해 둔 절차라는 비유입니다. Stored Procedure 자체가 업무 승인을 자동으로 보장하지는 않으며, 실제 호출 권한과 입력 검사는 따로 설계해야 합니다.

Trigger는 원래 SQL과 같은 트랜잭션 안에서 실행될 수 있어, 느리거나 실패하면 원래 작업에도 영향을 줍니다.

On-Premises·DBaaS: 운영 장소가 바뀌어도 책임은 남는다

On-Premises는 서버와 DB 운영 환경을 조직이 직접 준비하고 관리하는 방식입니다. Cloud DB는 Cloud 환경에서 운영되는 데이터베이스라는 큰 범주이고, DBaaS는 그중 제품과 설정에 따라 공급자가 설치·패치·일부 백업 같은 운영 작업을 맡는 관리형 제공 방식입니다.

패치

오류나 보안 문제를 고치기 위해 소프트웨어를 갱신하는 작업.

DBaaS로 감자 식당의 주문 DB를 관리형 서비스에 맡겼다고 보면, 공급자는 제품과 계약 범위 안에서 DB 설치·패치·일부 백업 기반을 맡습니다. 식당은 스키마와 SQL, 사용자 권한, 데이터 보호와 복구 검증을 맡습니다. 서비스 비용을 냈다고 문단속까지 자동으로 끝나지는 않습니다.

Backup·Replication·Failover·PITR: 비슷해 보여도 해결하는 사고가 다르다

  • Backup은 삭제나 손상 뒤 복구하기 위해 따로 보관하는 사본입니다.
  • Replication은 주 DB의 변경을 다른 DB가 계속 따라 받는 구성입니다.
  • Failover는 주 DB 장애 때 대기 DB가 주 역할을 이어받는 전환입니다.
  • PITR은 백업과 변경 기록을 이용해 지정한 과거 시점으로 복구하는 방식입니다.

이처럼 일부 구성요소가 고장 나도 서비스를 계속하거나 빠르게 재개하는 구조를 고가용성(High Availability)이라고 부릅니다.

낯선 말 1개눌러서 뜻 보기
복제본

원본 데이터의 변경을 전달받아 비슷한 상태를 유지하는 사본.

Replication은 주 DB의 변경을 따라 찍는 복사기라서, 실수로 누른 삭제도 복제본에 전달될 수 있습니다. 삭제까지 따라 하는 팀워크가 너무 좋습니다. Backup은 과거 사본을 보관하는 타임캡슐이고, PITR은 그 기록으로 지정한 과거 시점까지 되돌리는 방법입니다. Replication이 있어도 둘은 따로 준비해야 합니다.

나머지 운영 용어: 해결하는 문제만 구분한다

낯선 말 3개눌러서 뜻 보기
역할

여러 사용자에게 함께 줄 수 있도록 권한을 묶어 놓은 단위.

권한

조회·추가·수정처럼 특정 작업을 허용하는 범위.

파라미터

함수나 SQL을 실행할 때 바깥에서 전달하는 값.

  • OLTP·OLAP·DWH: 지금 주문을 처리하는 일, 많은 기록을 분석하는 일, 분석용 데이터를 모아 두는 저장소를 구분합니다.
  • 인증·인가: 누구인지 확인한 뒤 무엇을 할 수 있는지 나눕니다. 필요한 권한만 주고, 사용자 입력은 파라미터로 분리합니다.
  • TPS·QPS·Latency: 초당 처리량과 한 작업의 지연 시간을 보는 지표입니다. 숫자는 신호일 뿐, 원인은 로그와 실행 계획으로 다시 좁힙니다.

업무에 필요한 권한만 주는 최소 권한이 기본입니다. 파라미터 바인딩은 SQL 구조와 입력값을 분리해 SQL Injection 위험을 줄이는 방법입니다.

상세 설명

감자 식당 운영 본부

아래 Function·Procedure·Trigger가 DB에 미리 만들어져 있다고 가정하고, 주문 한 건이 들어온 뒤의 흐름을 따라가 봅시다.

-- Step 1: 금액 계산
SELECT line_total(2, 6000);

-- Step 2: 승인된 주문 처리 절차 실행
CALL register_order(17, 2);

-- Step 3: 자동 기록
-- Procedure 안의 INSERT 뒤에 설정된 Trigger가
-- 감사 로그 함수를 자동 실행한다.
  1. Step 1 — 계산 기능: Function이 수량과 단가로 결과값을 만듭니다.
  2. Step 2 — 처리 절차: Procedure가 주문 저장과 재고 변경을 실행합니다.
  3. Step 3 — 자동 규칙: Trigger가 주문 INSERT 뒤 감사 기록을 남깁니다.

이 자동 주문 코드와 별개로, 실제 서비스를 운영할 때는 두 관계를 반드시 구분합니다.

  • 관리형이어도 남는 책임: DBaaS가 운영 일부를 맡아도 사용자는 스키마·SQL·권한·복구 정책을 결정하고 검증합니다.
  • 복제본은 Backup이 아님: Replication은 장애 대응을 돕지만 잘못 삭제한 내용도 따라갈 수 있으므로, 과거로 돌아갈 Backup·PITR이 따로 필요합니다.

수업에서 OLTP·OLAP·DWH는 주문 처리와 분석의 구분, 인증·인가는 신원 확인과 허용 작업의 구분, TPS·QPS·Latency는 처리량과 지연을 뜻합니다.

자동화는 사람을 없애는 마법이 아닙니다. 반복 작업을 정해진 위치에 맡기고, 실패했을 때 찾고 되돌릴 수 있게 만드는 운영 방식입니다.

위의 CREATE TRIGGER 설정은 이미 완료됐습니다. 이제 한 행의 INSERT를 실행하면 어떤 흐름이 이어질까요?

AFTER INSERT ON potato_shop.orders
FOR EACH ROW
EXECUTE FUNCTION potato_shop.log_new_order();

INSERT INTO potato_shop.orders
