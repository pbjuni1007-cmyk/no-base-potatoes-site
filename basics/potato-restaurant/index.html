API와 이벤트

감자 식당은 주문을 어떻게 받는가

요청·응답과 이벤트 반응이 각각 상태를 바꾸는 흐름을 구분합니다.

  • API
  • 요청
  • 응답
  • 상태
  • 반응형
  • 이벤트
  • 리스너
  • 핸들러
  • 콜백
  • 페이로드

말 뜻부터 잡고 갑니다

코드에서 데이터는 다루려는 정보, 함수는 실행할 일을 묶은 코드, 호출은 그 함수를 실행해 달라고 요청하는 일입니다. 이 세 말을 바탕으로 감자 주문이 움직이는 순서를 봅니다.

주문을 보내는 쪽

  • API: 다른 코드가 기능을 사용할 수 있도록 공개한 약속과 사용법입니다. 웹 서버의 주소만 뜻하지 않고, 함수·객체·브라우저 기능도 API가 될 수 있습니다.
  • 이 글은 넓은 API 중에서 웹 서버의 HTTP API를 예로 사용합니다. 아래의 요청·응답·페이로드는 이 사례의 흐름입니다.
  • 요청과 응답: 필요한 일을 해 달라고 보내는 메시지가 요청, 처리 뒤 돌아오는 결과가 응답입니다.
  • 페이로드(payload): 요청이나 응답에 실어 보내는 실제 데이터입니다. 모든 요청에 반드시 페이로드가 있는 것은 아닙니다.
  • 상태(state): 프로그램이 지금 기억하고 있는 값입니다. 다음 행동이나 화면을 결정할 때 사용합니다.

어떤 일이 생긴 뒤 반응하는 쪽

  • 이벤트(event): 클릭·키 입력·로딩 완료처럼 “어떤 일이 발생했다”는 알림과 그 정보입니다.
  • 리스너(listener): 특정 이벤트가 생겼을 때 알림을 받도록 등록한 함수나 객체입니다. 아래 코드에서는 handleReady입니다.
  • 핸들러(handler): 이벤트를 받아 실제 행동을 처리하는 코드의 역할입니다. 아래 코드에서는 같은 handleReady가 이 역할도 합니다.
  • 콜백(callback): 다른 함수에 전달해 두면, 그 함수가 필요한 시점에 호출하는 함수입니다. 이벤트 핸들러가 콜백일 수 있지만 모든 콜백이 이벤트 핸들러인 것은 아닙니다.
  • 반응형(reactivity): 상태가 바뀌면 연결된 계산이나 화면을 자동으로 다시 맞추는 방식입니다. 일반 JavaScript 변수의 기본 기능은 아닙니다.

주문 요청과 이벤트 반응은 다른 흐름입니다

감자 식당 한 장면 안에서도 두 줄을 따로 읽어야 합니다.

첫 흐름은 다른 기능에 일을 요청하고 결과를 받는 과정입니다. 두 번째 흐름은 이미 생긴 일을 알리고 그에 반응하는 과정입니다. 둘 다 상태를 바꿀 수 있지만 같은 메커니즘은 아닙니다.

한 코드에서 두 흐름 따라가기

HTML에 id="ready-button"인 음식 완료 버튼과 id="order-status"인 주문 현황판이 있다고 가정합니다. 서버의 /api/orders 주소는 { menu: '감자튀김', table: 3, status: '조리 중' } 같은 주문 결과를 JSON으로 돌려줍니다.

document.querySelector()는 HTML에서 버튼을 찾습니다. fetch()는 JavaScript가 호출하는 브라우저 API이고, 브라우저는 서버의 /api/orders 주소로 HTTP 요청을 보냅니다. async와 await는 응답을 기다린 뒤 다음 줄을 실행하기 위한 문법입니다. 지금은 이 문법을 외우지 않고 두 흐름의 순서만 봅니다.

const orderState = {
  status: '주문 전',
  order: null,
}

const statusBoard = document.querySelector('#order-status')
const readyButton = document.querySelector('#ready-button')
readyButton.disabled = true

function render() {
  statusBoard.textContent = orderState.status
}

// 흐름 1: 브라우저 fetch API로 서버 HTTP API에 주문 요청 보내기
async function submitOrder(payload) {
  const response = await fetch('/api/orders', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(payload),
  })

  orderState.order = await response.json()
  orderState.status = orderState.order.status
  render()
  readyButton.disabled = false
}

// 흐름 2: click event를 처리하는 handler
function handleReady(event) {
  orderState.status = '준비 완료'
  render()
}

readyButton.addEventListener('click', handleReady)

submitOrder({ menu: '감자튀김', table: 3 })

코드에서는 다음 변화만 추적하면 됩니다.

  1. 처음 상태는 주문 전입니다.
  2. submitOrder()가 { menu: '감자튀김', table: 3 }을 페이로드로 보냅니다.
  3. 서버 응답을 받은 뒤 상태는 응답 속 status로 바뀌고 완료 버튼이 열립니다.
  4. 완료 버튼을 누르면 click 이벤트가 발생합니다.
  5. addEventListener()에 등록된 handleReady가 실행되어 상태를 준비 완료로 바꿉니다.

이 코드의 handleReady는 addEventListener()에 등록된 리스너이며, 이벤트를 처리하는 핸들러입니다. 다른 함수에 전달되었으므로 콜백이기도 합니다. 일반 JavaScript에서는 상태만 바꿔도 화면이 저절로 바뀌지 않아 render()를 직접 호출했습니다. Vue의 반응형 상태는 이런 연결을 자동화하는 도구입니다.

식당 비유가 맞는 곳과 깨지는 곳

  • API — 주문 방법과 창구: 사용 규칙을 기억하기에는 맞습니다. 하지만 API는 물리적인 창구가 아닙니다. 함수·객체·브라우저 기능이 API가 될 수 있고, 서버 HTTP API에는 사용할 주소와 규칙이 포함될 수 있습니다.
  • 페이로드 — 주문서의 메뉴와 테이블 번호: 실어 보내는 데이터를 기억하기에는 맞습니다. 하지만 문자열·JSON·파일 등 형식이 다양하고 데이터가 없는 요청도 있습니다.
  • 상태 — 현재 주문 현황판: 지금 기억하는 값을 떠올리기에는 맞습니다. 하지만 상태가 언제나 한 화면에 모여 있는 것은 아닙니다.
  • 이벤트 — 음식 완료 벨: 이미 일어난 일을 알린다는 점은 맞습니다. 하지만 사용자뿐 아니라 브라우저나 다른 코드도 이벤트를 만들 수 있습니다.
  • 리스너·핸들러 — 벨을 받도록 등록된 직원과 그 직원의 행동: 등록과 처리라는 관점을 나눠 기억하기에는 맞습니다. 하지만 둘이 항상 별도 코드인 것은 아니며, 하나의 함수가 리스너이자 핸들러인 일이 흔합니다.
  • 반응형 — 주문판을 바꾸면 전광판도 갱신: 연결된 값이 따라 바뀐다는 점은 맞습니다. 하지만 자동 연결 장치가 있을 때만 성립하며, 일반 변수는 화면을 자동으로 바꾸지 않습니다.
