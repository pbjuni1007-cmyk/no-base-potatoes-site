중심 질문: 요청 흐름과 이벤트 흐름은 어떻게 다를까요?

코드에서 데이터는 다루려는 정보, 함수는 실행할 일을 묶은 코드, 호출은 그 함수를 실행해 달라고 요청하는 일입니다. 이 세 말을 바탕으로 감자 주문이 움직이는 두 흐름을 구분합니다.

주문을 보내는 쪽

  • API: 다른 코드가 기능을 사용할 수 있도록 공개한 약속과 사용법입니다. 웹 서버의 주소만 뜻하지 않고, 함수·객체·브라우저 기능도 API가 될 수 있습니다.
  • 이 글은 넓은 API 중에서 웹 서버의 HTTP API를 예로 사용합니다. 아래의 요청·응답·페이로드는 이 사례의 흐름입니다.
  • HTTP: 브라우저와 서버가 웹에서 요청과 응답을 주고받는 규칙입니다.
  • JSON: 객체·배열·문자열·숫자·불리언·null 같은 값을 텍스트로 표현하는 데이터 형식입니다. JavaScript 객체를 그대로 부르는 이름이 아닙니다.
  • 요청과 응답: 필요한 일을 해 달라고 보내는 메시지가 요청, 처리 뒤 돌아오는 결과가 응답입니다.
  • 페이로드(payload): 요청이나 응답에 실어 보내는 실제 데이터입니다. 모든 요청에 반드시 페이로드가 있는 것은 아닙니다.
  • 상태(state): 프로그램이 지금 기억하고 있는 값입니다. 다음 행동이나 화면을 결정할 때 사용합니다.

어떤 일이 생긴 뒤 반응하는 쪽

  • 이벤트(event): 클릭·키 입력·로딩 완료처럼 “어떤 일이 발생했다”는 알림과 그 정보입니다.
  • 리스너(listener): 특정 이벤트가 생겼을 때 알림을 받도록 등록한 함수나 객체입니다. 아래 코드에서는 handleReady입니다.
  • 핸들러(handler): 이벤트를 받아 실제 행동을 처리하는 코드의 역할입니다. 아래 코드에서는 같은 handleReady가 이 역할도 합니다.
  • 콜백(callback): 다른 함수에 전달해 두면, 그 함수가 필요한 시점에 호출하는 함수입니다. 이벤트 핸들러가 콜백일 수 있지만 모든 콜백이 이벤트 핸들러인 것은 아닙니다.
  • 반응형(reactivity): 상태가 바뀌면 연결된 계산이나 화면을 자동으로 다시 맞추는 방식입니다. 일반 JavaScript 변수의 기본 기능은 아닙니다.

주문 요청과 이벤트 반응은 다른 흐름입니다

감자 식당 한 장면 안에서도 두 줄을 따로 읽어야 합니다.

첫 흐름은 다른 기능에 일을 요청하고 결과를 받는 과정입니다. 요청을 보낸 코드는 응답을 기다리고, 응답에 든 데이터를 읽습니다.

두 번째 흐름은 이미 생긴 일을 알리고 그에 반응하는 과정입니다. 브라우저가 클릭 이벤트를 알리면 미리 등록한 함수가 실행됩니다. 둘 다 상태를 바꿀 수 있지만 같은 메커니즘은 아닙니다.

요청 흐름: payload 준비 → fetch 요청 → 서버 응답 → state 변경 → render
이벤트 흐름: click 발생 → 등록된 handleReady 실행 → state 변경 → render

두 흐름을 따로 따라가기

서버가 돌려주는 JSON 텍스트는 다음처럼 키와 문자열을 큰따옴표로 적습니다.

{"menu":"감자튀김","table":3,"status":"조리 중"}

아래 두 코드는 같은 화면의 서로 다른 부분입니다. 이미 주문 전 상태를 가진 orderState, 상태를 화면에 옮기는 render(), 완료 버튼 readyButton이 준비되어 있고 두 코드가 이를 함께 사용한다고 가정합니다.

1. 요청하고 응답받기

async function submitOrder(payload) {
  const response = await fetch('/api/orders', {
    method: 'POST',
    body: JSON.stringify(payload),
  })

  const order = await response.json()
  orderState.status = order.status
  render()
}

submitOrder({ menu: '감자튀김', table: 3 })

payload를 JSON 텍스트로 바꿔 요청하고, 응답의 status를 읽어 상태를 주문 전 → 조리 중으로 바꿉니다. 일반 JavaScript 상태는 화면을 자동으로 바꾸지 않으므로 마지막에 render()를 호출합니다.

2. 클릭 이벤트에 반응하기

function handleReady() {
  if (orderState.status !== '조리 중') return

  orderState.status = '준비 완료'
  render()
}

readyButton.addEventListener('click', handleReady)

버튼을 누르면 click 이벤트가 발생합니다. 아직 조리 중이 아니면 첫 줄에서 끝나므로 상태를 건너뛸 수 없습니다. 요청 응답으로 조리 중이 된 뒤에만 handleReady가 상태를 준비 완료로 바꾸고 화면을 갱신합니다. 이 함수는 등록된 리스너, 이벤트를 처리하는 핸들러, 다른 함수에 전달된 콜백 역할을 동시에 합니다.

따라서 상태의 정상 순서는 주문 전 → 조리 중 → 준비 완료이며, 중간 상태를 건너뛰는 클릭은 가드에서 멈춥니다.

요청 흐름: payload → fetch → 응답 → 조리 중 → render
이벤트 흐름: click → 조리 중인지 확인 → 준비 완료 → render

식당 비유가 맞는 곳과 깨지는 곳

  • API — 주문 방법과 창구: 사용 규칙을 기억하기에는 맞습니다. 하지만 API는 물리적인 창구가 아닙니다. 함수·객체·브라우저 기능이 API가 될 수 있고, 서버 HTTP API에는 사용할 주소와 규칙이 포함될 수 있습니다.
  • 페이로드 — 주문서의 메뉴와 테이블 번호: 실어 보내는 데이터를 기억하기에는 맞습니다. 하지만 문자열·JSON·파일 등 형식이 다양하고 데이터가 없는 요청도 있습니다.
  • 상태 — 현재 주문 현황판: 지금 기억하는 값을 떠올리기에는 맞습니다. 하지만 상태가 언제나 한 화면에 모여 있는 것은 아닙니다.
  • 이벤트 — 음식 완료 벨: 이미 일어난 일을 알린다는 점은 맞습니다. 하지만 사용자뿐 아니라 브라우저나 다른 코드도 이벤트를 만들 수 있습니다.
  • 리스너·핸들러 — 벨을 받도록 등록된 직원과 그 직원의 행동: 등록과 처리라는 관점을 나눠 기억하기에는 맞습니다. 하지만 둘이 항상 별도 코드인 것은 아니며, 하나의 함수가 리스너이자 핸들러인 일이 흔합니다.
  • 반응형 — 주문판을 바꾸면 전광판도 갱신: 연결된 값이 따라 바뀐다는 점은 맞습니다. 하지만 자동 연결 장치가 있을 때만 성립하며, 일반 변수는 화면을 자동으로 바꾸지 않습니다.
