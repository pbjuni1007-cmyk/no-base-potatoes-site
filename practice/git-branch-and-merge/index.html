오늘의 미션

nobase-practice/git-branch-and-merge 저장소의 feature/add-check-tip 브랜치에서 작은 변경을 커밋한 뒤 main으로 돌아와 차이를 확인하고 병합합니다. 마지막에는 기능 커밋이 main 기록에 포함됐다는 증거를 보고, 병합된 로컬 브랜치를 안전하게 정리합니다.

시작 상태와 안전선

Git 01을 하지 않았어도 이 글 안에서 필요한 시작 저장소를 만들 수 있습니다. 이번 글은 로컬 브랜치만 사용하며 GitHub, 원격 저장소와 공유 브랜치는 사용하지 않습니다. 아래에서는 명령을 한 줄씩 입력하고 결과를 확인한 뒤 다음 줄로 넘어갑니다.

mkdir는 폴더를 만드는 명령이고, -p는 상위 폴더가 이미 있어도 오류 없이 필요한 폴더만 준비하는 옵션입니다. 이번 한 줄에서는 모든 실습이 함께 사용할 nobase-practice 폴더를 준비합니다.

mkdir -p ~/nobase-practice

성공하면 아무것도 출력되지 않습니다. 오류가 보이면 다음 명령을 입력하지 말고 오류에 나온 경로와 철자를 확인합니다.

cd는 현재 위치를 다른 폴더로 옮기는 명령입니다. 이번 한 줄에서는 방금 준비한 공통 실습 폴더로 이동합니다.

cd ~/nobase-practice

성공하면 아무것도 출력되지 않습니다. no such file or directory가 보이면 다음 명령을 입력하지 말고 앞의 mkdir 명령과 경로를 다시 확인합니다.

ls는 현재 폴더에 있는 이름을 보여 주는 명령입니다. 이번 한 줄에서는 같은 이름의 실습 폴더가 이미 있는지 확인합니다.

ls

기존 파일과 폴더 이름이 출력되거나, 비어 있으면 아무것도 출력되지 않습니다. 여기서 git-branch-and-merge가 보이면 중단합니다. 그 경로로 들어가거나, 지우거나, 파일을 추가하지 말고 강사에게 기존 실습을 어떻게 보관할지 확인합니다.

옵션 없는 mkdir는 같은 이름이 이미 있으면 실패하므로 기존 경로를 바꾸지 않습니다. 이번 한 줄에서는 이 글만 사용할 새 폴더를 만듭니다.

mkdir git-branch-and-merge

성공하면 아무것도 출력되지 않습니다. File exists 같은 오류가 보이면 기존 경로를 사용하지 말고 여기서 중단합니다.

이번 한 줄에서는 새로 만든 이 글의 실습 폴더로 이동합니다.

cd git-branch-and-merge

성공하면 아무것도 출력되지 않습니다. 오류가 보이면 다음 명령을 입력하지 말고 앞의 mkdir 결과와 현재 이름을 확인합니다.

touch는 없는 파일을 빈 파일로 만드는 명령입니다. 이번 한 줄에서는 이 글에서 새로 만든 폴더임을 나타내는 안전 표식 파일을 만듭니다.

touch .nobase-practice-root

성공하면 아무것도 출력되지 않습니다. 오류가 보이면 다음 명령을 입력하지 말고 현재 폴더의 쓰기 권한과 철자를 확인합니다.

pwd는 현재 폴더의 전체 경로를 보여 줍니다. 이번 한 줄에서는 정확한 실습 폴더에 들어왔는지 확인합니다.

pwd

출력 끝이 /nobase-practice/git-branch-and-merge여야 합니다. 다르면 다음 명령을 입력하지 말고 cd 단계부터 경로를 다시 확인합니다.

ls -la의 -l은 자세한 정보, -a는 점으로 시작하는 숨김 파일까지 보여 주는 옵션입니다. 이번 한 줄에서는 안전 표식이 실제로 생겼는지 확인합니다.

ls -la

목록에 .nobase-practice-root가 보여야 합니다. 보이지 않으면 다음 명령을 입력하지 말고 touch 명령의 철자를 확인합니다.

git --version은 설치된 Git 버전을 보여 줍니다. 이번 한 줄에서는 실습에 필요한 Git 2.28 이상인지 확인합니다.

git --version

git version 2.28.0처럼 버전이 출력됩니다. 2.28보다 낮거나 명령을 찾을 수 없다는 오류가 나오면 저장소를 만들지 말고 Git 설치 상태를 먼저 확인합니다.

시작 파일과 첫 커밋 준비하기

이번 한 줄에서는 README와 Git 제외 규칙 파일을 빈 파일로 만듭니다.

touch README.md .gitignore

성공하면 아무것도 출력되지 않습니다. 오류가 보이면 다음 명령을 입력하지 말고 pwd와 ls -la로 현재 위치와 만들어진 이름을 확인합니다.

macOS의 open -a는 지정한 앱으로 파일을 여는 명령입니다. 이번 한 줄에서는 두 파일을 Visual Studio Code로 엽니다.

open -a "Visual Studio Code" README.md .gitignore

터미널에는 보통 아무것도 출력되지 않고 VS Code 창이나 탭이 열립니다. 앱을 찾을 수 없다는 오류가 보이면 파일 내용을 입력하지 말고 VS Code의 설치 이름을 확인합니다.

README.md에 다음 두 줄을 입력하고 저장합니다.

# Branch Practice
브랜치의 차이를 확인합니다.

.gitignore에는 다음 세 줄을 입력하고 저장합니다.

.DS_Store
.env
.nobase-practice-root

cat은 파일 내용을 터미널에 보여 줍니다. 이번 한 줄에서는 README가 정확히 저장됐는지 확인합니다.

cat README.md

제목과 설명 두 줄이 보여야 합니다. 다르면 다음 명령을 입력하지 말고 VS Code에서 파일을 고쳐 저장합니다.

이번 한 줄에서는 Git에서 제외할 보호 규칙을 확인합니다.

cat .gitignore

.DS_Store, .env, .nobase-practice-root가 한 줄씩 보여야 합니다. 다르면 저장소를 만들기 전에 .gitignore를 고쳐 저장합니다.

git init은 현재 폴더를 Git 저장소로 만들고, -b main은 첫 브랜치 이름을 main으로 정합니다. 이번 한 줄에서는 현재 실습 폴더에서 저장소를 시작합니다.

git init -b main

초기화했다는 문장과 현재 경로가 출력됩니다. 오류가 보이면 다음 명령을 입력하지 말고 pwd, ls -la, git --version을 차례로 다시 확인합니다.

git config --local은 설정을 현재 저장소에만 기록합니다. 이번 한 줄에서는 연습 커밋에 표시할 이름을 로컬 설정으로 저장합니다.

git config --local user.name "Practice Learner"

성공하면 아무것도 출력되지 않습니다. 오류가 보이면 다음 명령을 입력하지 말고 현재 폴더에 .git이 있는지 ls -la로 확인합니다.

이번 한 줄에서는 실제 주소가 아닌 연습용 이메일을 현재 저장소에만 저장합니다.

git config --local user.email "practice@example.invalid"

성공하면 아무것도 출력되지 않습니다. example.invalid는 실제 메일 전송에 사용되지 않는 연습용 도메인입니다. 오류가 보이면 커밋 단계로 넘어가지 말고 로컬 저장소 초기화 상태를 확인합니다.

이번 한 줄에서는 저장된 로컬 사용자 이름을 확인합니다.

git config --local user.name

Practice Learner가 출력되어야 합니다. 다르면 다음 명령을 입력하지 말고 앞의 이름 설정 명령을 다시 확인합니다.

이번 한 줄에서는 저장된 로컬 연습 이메일을 확인합니다.

git config --local user.email

practice@example.invalid가 출력되어야 합니다. 다르면 다음 명령을 입력하지 말고 앞의 이메일 설정 명령을 다시 확인합니다.

git status --short의 --short는 현재 변경을 짧은 기호로 보여 줍니다. 이번 한 줄에서는 첫 git add 전에 파일 상태를 확인합니다.

git status --short

.gitignore와 README.md 앞에 ??가 보이고, 안전 표식과 .env는 보이지 않아야 합니다. 예상하지 못한 파일이 보이면 git add를 입력하지 말고 파일 이름과 내용을 확인합니다.

git diff는 작업 폴더와 스테이징 영역의 차이를 보여 줍니다. 이번 한 줄에서는 첫 git add 전에 아직 스테이징하지 않은 차이를 확인합니다.

git diff

새 파일은 아직 Git이 추적하지 않으므로 아무것도 출력되지 않을 수 있습니다. 이 빈 출력은 오류가 아닙니다. 오류가 보이면 git add를 입력하지 말고 앞의 상태를 확인합니다.

git diff --staged의 --staged는 다음 커밋에 들어가도록 고른 변경만 보여 줍니다. 이번 한 줄에서는 스테이징 영역이 아직 비어 있는지 확인합니다.

git diff --staged

아직 아무것도 고르지 않았으므로 성공하면 아무것도 출력되지 않습니다. 내용이 보이면 git add를 입력하지 말고 이미 스테이징된 파일 이름을 확인합니다.

git add는 다음 커밋에 넣을 파일을 스테이징 영역에 고릅니다. 이번 한 줄에서는 확인한 두 파일을 첫 커밋 대상으로 고릅니다.

git add .gitignore README.md

성공하면 아무것도 출력되지 않습니다. 오류가 보이면 다음 명령을 입력하지 말고 오류에 나온 파일 이름과 ls -la 결과를 확인합니다.

이번 한 줄에서는 git add 뒤 두 파일이 스테이징됐는지 확인합니다.

git status --short

두 파일 앞에 A 가 보여야 합니다. 다른 파일이나 ??가 보이면 커밋하지 말고 파일 목록을 다시 확인합니다.

이번 한 줄에서는 첫 커밋에 들어갈 실제 내용을 확인합니다.

git diff --staged

README 두 줄과 .gitignore 세 줄만 보여야 합니다. .env, 안전 표식, 실제 이메일, 키 같은 내용이 보이면 커밋하지 말고 원인을 먼저 확인합니다.

git commit -m의 -m은 커밋 설명을 명령 안에 적는 옵션입니다. 이번 한 줄에서는 확인한 두 파일을 시작 커밋으로 남깁니다.

git commit -m "docs: start branch practice"

성공하면 커밋 식별자, 메시지, 변경된 파일 수가 출력됩니다. 오류가 보이면 다음 명령을 입력하지 말고 오류 문장과 git status --short 결과를 확인합니다.

이번 한 줄에서는 첫 커밋 뒤 작업 폴더에 남은 변경이 없는지 확인합니다.

git status --short

성공했고 모든 변경을 커밋했다면 아무것도 출력되지 않습니다. 파일 이름이 보이면 새 브랜치를 만들지 말고 남은 변경을 확인합니다.

git log --oneline --decorate -1은 최근 기록 한 개를 짧게 보여 주고 현재 브랜치 표시도 붙입니다. 이번 한 줄에서는 시작 커밋이 main에 남았는지 확인합니다.

git log --oneline --decorate -1

컴퓨터마다 다른 짧은 해시와 함께 (HEAD -> main) 및 docs: start branch practice가 보여야 합니다. 다르면 새 브랜치를 만들지 말고 현재 기록을 확인합니다.

처음 만나는 말

  • 브랜치(branch): 특정 커밋을 가리키는 움직일 수 있는 이름입니다.
  • HEAD: 지금 체크아웃해 작업 중인 브랜치나 커밋을 가리킵니다.
  • 전환(switch): 작업할 브랜치를 바꾸고 그 상태의 파일을 작업 폴더에 보여 줍니다.
  • 병합(merge): 다른 브랜치의 변경 기록을 현재 브랜치에 포함합니다.
  • fast-forward: 현재 브랜치 뒤에 다른 브랜치 커밋이 일직선으로 이어질 때 포인터만 앞으로 옮기는 병합입니다.

브랜치는 프로젝트 폴더 전체를 하나 더 복사하는 기능이 아닙니다. 브랜치마다 어떤 커밋을 가리키는지가 달라지고, 전환하면 그 커밋에 맞는 파일 상태가 보입니다.

명령을 직접 입력하기

1. 기능 브랜치 만들기

git switch -c의 -c는 새 브랜치를 만들면서 바로 그 브랜치로 전환하는 옵션입니다. 이번 한 줄에서는 feature/add-check-tip 브랜치를 만들고 전환합니다.

git switch -c feature/add-check-tip

Switched to a new branch와 새 브랜치 이름이 출력됩니다. 오류가 보이면 다음 명령을 입력하지 말고 오류 문장과 현재 상태를 확인합니다.

git branch --show-current는 현재 브랜치 이름만 보여 줍니다. 이번 한 줄에서는 전환한 브랜치 이름을 확인합니다.

git branch --show-current

feature/add-check-tip이 출력되어야 합니다. 다르면 파일을 수정하지 말고 현재 브랜치를 확인합니다.

이번 한 줄에서는 새 브랜치의 작업 폴더가 깨끗한지 확인합니다.

git status --short

아무것도 출력되지 않아야 합니다. 파일 이름이 보이면 README를 열지 말고 남은 변경부터 확인합니다.

2. 브랜치에서만 변경하고 커밋하기

이번 한 줄에서는 README를 Visual Studio Code로 엽니다.

open -a "Visual Studio Code" README.md

터미널에는 보통 아무것도 출력되지 않고 README 탭이 열립니다. 오류가 보이면 파일을 수정하지 말고 앱 이름과 ls의 파일 이름을 확인합니다.

파일 끝에 다음 한 줄을 추가하고 저장합니다.

- 실행 전후에 pwd와 git status를 확인한다.

이번 한 줄에서는 커밋 전에 README의 Git 상태를 확인합니다.

git status --short

README.md 앞에 M이 보여야 합니다. 보이지 않으면 git add를 입력하지 말고 VS Code에서 저장했는지 확인합니다.

이번 한 줄에서는 커밋 전에 추가한 실제 문장을 확인합니다.

git diff

추가한 문장 앞에 +가 붙어 보여야 합니다. 다른 변경이 보이면 git add를 입력하지 말고 README 내용을 확인합니다.

이번 한 줄에서는 확인한 README만 스테이징합니다.

git add README.md

성공하면 아무것도 출력되지 않습니다. 오류가 보이면 다음 명령을 입력하지 말고 README 이름과 현재 위치를 확인합니다.

이번 한 줄에서는 git add 뒤 README가 스테이징됐는지 확인합니다.

git status --short

README.md 앞에 M 이 보여야 합니다. 다르면 커밋하지 말고 현재 상태를 확인합니다.

이번 한 줄에서는 기능 커밋에 들어갈 실제 차이를 확인합니다.

git diff --staged

추가한 문장 한 줄만 보여야 합니다. 다른 변경이 보이면 커밋하지 않습니다.

이번 한 줄에서는 확인한 README 변경을 기능 커밋으로 남깁니다.

git commit -m "docs: add state check tip"

성공하면 새 커밋 식별자와 메시지가 출력됩니다. 오류가 보이면 다음 명령을 입력하지 말고 오류 문장과 상태를 확인합니다.

이번 한 줄에서는 기능 커밋 뒤 남은 변경이 없는지 확인합니다.

git status --short

성공하면 아무것도 출력되지 않습니다. 파일 이름이 보이면 main으로 전환하지 말고 남은 변경을 확인합니다.

git log --oneline --decorate --graph --all -4는 모든 로컬 브랜치의 최근 기록을 최대 네 줄의 간단한 그래프로 보여 줍니다. 이번 한 줄에서는 기능 브랜치가 새 커밋을 가리키는지 확인합니다.

git log --oneline --decorate --graph --all -4

최신 줄에 (HEAD -> feature/add-check-tip)과 기능 커밋 메시지가 보이고, 그 아래에 main의 시작 커밋이 보여야 합니다. 다르면 main으로 전환하지 말고 로그를 다시 읽습니다.

3. main과 feature의 차이 보기

git switch는 기존 브랜치로 전환합니다. 이번 한 줄에서는 시작 커밋을 가리키는 main으로 돌아갑니다.

git switch main

Switched to branch 'main'이 출력됩니다. 오류가 보이면 다음 명령을 입력하지 말고 오류 문장과 현재 브랜치를 확인합니다.

이번 한 줄에서는 현재 브랜치가 main인지 확인합니다.

git branch --show-current

main이 출력되어야 합니다. 다르면 병합하지 말고 현재 브랜치를 확인합니다.

이번 한 줄에서는 전환 뒤 작업 폴더가 깨끗한지 확인합니다.

git status --short

아무것도 출력되지 않아야 합니다. 파일 이름이 보이면 병합하지 말고 남은 변경을 확인합니다.

git diff main..feature/add-check-tip은 main과 기능 브랜치가 가리키는 파일 상태의 차이를 보여 줍니다. 이번 한 줄에서는 병합 전에 기능 브랜치에만 있는 변경을 확인합니다.

git diff main..feature/add-check-tip

README에 추가한 문장 앞에 +가 붙어 보여야 합니다. 다른 변경이 보이거나 오류가 나면 병합하지 말고 브랜치 이름과 로그를 확인합니다.

4. main에서 병합하고 검증하기

git merge --ff-only의 --ff-only는 기록이 일직선으로 이어질 때만 병합하고, 그렇지 않으면 멈추는 안전 옵션입니다. 이번 한 줄에서는 확인한 기능 브랜치를 현재 main에 병합합니다.

git merge --ff-only feature/add-check-tip

정상 흐름에서는 Fast-forward와 바뀐 파일 정보가 출력됩니다. 오류가 보이면 다음 명령을 입력하지 말고 오류 문장, 현재 브랜치, 상태, 로그를 확인합니다.

이번 한 줄에서는 병합 뒤 작업 폴더가 깨끗한지 확인합니다.

git status --short

성공하면 아무것도 출력되지 않습니다. 파일 이름이 보이면 브랜치를 삭제하지 말고 남은 변경을 확인합니다.

이번 한 줄에서는 병합 뒤 main과 기능 브랜치가 같은 최신 커밋을 가리키는지 확인합니다.

git log --oneline --decorate --graph --all -4

최신 기능 커밋 줄에 HEAD -> main과 feature/add-check-tip이 함께 보여야 합니다. 다르면 브랜치를 삭제하지 말고 로그를 확인합니다.

이번 한 줄에서는 병합된 문장이 README에도 있는지 확인합니다.

cat README.md

마지막에 - 실행 전후에 pwd와 git status를 확인한다.가 보여야 합니다. 보이지 않으면 브랜치를 삭제하지 말고 병합 결과를 확인합니다.

5. 병합된 브랜치 정리하기

git branch -d의 소문자 -d는 병합되지 않은 작업이 있으면 삭제를 거부하는 안전 옵션입니다. 이번 한 줄에서는 병합이 확인된 기능 브랜치 이름을 정리합니다.

git branch -d feature/add-check-tip

삭제했다는 문장과 기능 브랜치 이름이 출력됩니다. 병합되지 않았다는 오류가 보이면 강제 삭제하지 말고 다음 단계로 가지 않습니다.

이번 한 줄에서는 남은 로컬 브랜치 이름을 확인합니다.

git branch

별표가 붙은 main만 보여야 합니다. 기능 브랜치가 남아 있으면 완료로 판정하지 말고 앞의 삭제 결과를 확인합니다.

이번 한 줄에서는 브랜치 정리 뒤 작업 폴더가 깨끗한지 확인합니다.

git status --short

아무것도 출력되지 않아야 합니다. 파일 이름이 보이면 완료로 판정하지 말고 변경을 확인합니다.

출력에서 확인할 것

  1. feature에서 커밋한 직후 두 브랜치가 서로 다른 커밋을 가리키는가?
  2. main으로 전환하면 feature에서 추가한 문장이 병합 전에는 보이지 않는가?
  3. 병합 뒤 main 로그와 README에 기능 변경이 포함됐는가?
  4. branch -d 뒤 기능 브랜치 이름만 사라지고 커밋 내용은 main에 남았는가?

정상 흐름 완료

이번 한 줄에서는 마지막 현재 경로를 확인합니다.

pwd

출력 끝이 /nobase-practice/git-branch-and-merge여야 합니다. 다르면 다른 명령을 입력하지 말고 실습 폴더로 돌아갑니다.

이번 한 줄에서는 안전 표식과 저장소 폴더를 함께 확인합니다.

ls -la

.nobase-practice-root와 .git이 모두 보여야 합니다. 하나라도 없으면 완료로 판정하지 않습니다.

이번 한 줄에서는 현재 브랜치 이름을 확인합니다.

git branch --show-current

main이 출력되어야 합니다. 다른 이름이 보이면 완료로 판정하지 않습니다.

이번 한 줄에서는 남은 로컬 브랜치를 확인합니다.

git branch

별표가 붙은 main만 보여야 합니다. 다른 브랜치가 보이면 정리 결과를 다시 확인합니다.

이번 한 줄에서는 마지막 Git 상태가 깨끗한지 확인합니다.

git status --short

아무것도 출력되지 않아야 합니다. 파일 이름이 보이면 완료로 판정하지 않습니다.

이번 한 줄에서는 main에 기능 커밋이 남아 있는지 확인합니다.

git log --oneline --decorate --graph -4

최신 줄에 (HEAD -> main)과 docs: add state check tip이 보여야 합니다. 다르면 완료로 판정하지 않습니다.

이번 한 줄에서는 병합한 문장이 실제 파일에 남아 있는지 확인합니다.

cat README.md

제목, 시작 설명, 기능 브랜치에서 추가한 문장이 모두 보여야 합니다. 하나라도 빠졌다면 완료로 판정하지 않습니다.

대표 실패와 복구

git switch 뒤에 존재하지 않는 브랜치 이름을 주면 Git은 전환하지 않고 오류를 보여 줍니다. 이번 한 줄에서는 일부러 만들지 않은 브랜치로 전환해 오류를 읽습니다.

git switch feature/not-created

잘못된 reference라는 오류가 보입니다. 새 브랜치를 무작정 만들거나 다른 이름을 추측하지 말고, 다음 확인 명령으로 현재 상태부터 읽습니다.

이번 한 줄에서는 실패 뒤 Git 상태가 바뀌지 않았는지 확인합니다.

git status --short

기존 상태가 깨끗하므로 아무것도 출력되지 않아야 합니다. 파일 이름이 보이면 다음 명령을 입력하지 말고 그 변경부터 확인합니다.

git branch --all의 --all은 로컬과 원격 브랜치 이름을 함께 보여 줍니다. 이번 한 줄에서는 실제로 존재하는 브랜치 이름을 확인합니다.

git branch --all

이 로컬 실습에서는 별표가 붙은 main만 보여야 합니다. 예상하지 못한 이름이 보이면 전환하지 말고 저장소가 맞는지 확인합니다.

이번 한 줄에서는 실패 뒤에도 현재 브랜치가 main인지 확인합니다.

git branch --show-current

main이 출력되어야 합니다. 다른 이름이 보이면 새 명령을 입력하지 말고 현재 위치와 브랜치 상태를 확인합니다.

완료 확인

실행 전에 새 브랜치에서 커밋하면 main과 로그가 어떻게 갈라질지 예측합니다.

힌트 없는 변형 과제: feature/add-next-step 브랜치를 만들고 README에 - 다음 명령을 고르기 전에 오류 문장을 읽는다.를 추가해 커밋하세요. main에서 차이를 증명한 뒤 --ff-only로 병합하고, 병합된 브랜치를 -d로 정리하세요. 마지막에는 branch, status, log, README 출력으로 결과를 설명합니다.

변형 과제 정답 확인하기
  1. 이번 한 줄에서는 새 기능 브랜치를 만들고 전환합니다.
git switch -c feature/add-next-step

새 브랜치로 전환했다는 문장이 출력됩니다. 오류가 보이면 다음 단계로 가지 않습니다.

  1. 이번 한 줄에서는 현재 브랜치 이름을 확인합니다.
git branch --show-current

feature/add-next-step이 출력되어야 합니다. 다르면 README를 수정하지 않습니다.

  1. 이번 한 줄에서는 README를 VS Code로 엽니다.
open -a "Visual Studio Code" README.md

터미널에는 보통 아무것도 출력되지 않고 README 탭이 열립니다. 오류가 보이면 파일을 수정하지 않습니다.

VS Code에서 - 다음 명령을 고르기 전에 오류 문장을 읽는다.를 추가하고 저장한 다음 계속합니다.

  1. 이번 한 줄에서는 저장한 README의 상태를 확인합니다.
git status --short

README.md 앞에 M이 보여야 합니다. 다르면 git add를 입력하지 않습니다.

  1. 이번 한 줄에서는 아직 스테이징하지 않은 차이를 확인합니다.
git diff

새 문장 한 줄만 추가된 모습이어야 합니다. 다른 변경이 보이면 진행하지 않습니다.

  1. 이번 한 줄에서는 확인한 README만 스테이징합니다.
git add README.md

성공하면 아무것도 출력되지 않습니다. 오류가 보이면 다음 단계로 가지 않습니다.

  1. 이번 한 줄에서는 README가 스테이징됐는지 확인합니다.
git status --short

README.md 앞에 M 이 보여야 합니다. 다르면 커밋하지 않습니다.

  1. 이번 한 줄에서는 커밋에 들어갈 실제 차이를 확인합니다.
git diff --staged

새 문장 한 줄만 보여야 합니다. 다른 변경이 보이면 커밋하지 않습니다.

  1. 이번 한 줄에서는 확인한 변경을 기능 커밋으로 남깁니다.
git commit -m "docs: add next step"

새 커밋 식별자와 메시지가 출력됩니다. 오류가 보이면 다음 단계로 가지 않습니다.

  1. 이번 한 줄에서는 커밋 뒤 상태가 깨끗한지 확인합니다.
git status --short

성공하면 아무것도 출력되지 않습니다. 파일 이름이 보이면 main으로 전환하지 않습니다.

  1. 이번 한 줄에서는 기능 브랜치 커밋과 main의 위치를 확인합니다.
git log --oneline --decorate --graph --all -4

최신 기능 커밋 아래에 main의 이전 커밋이 보여야 합니다. 다르면 전환하지 않습니다.

  1. 이번 한 줄에서는 main으로 전환합니다.
git switch main

main으로 전환했다는 문장이 출력됩니다. 오류가 보이면 병합하지 않습니다.

  1. 이번 한 줄에서는 현재 브랜치가 main인지 확인합니다.
git branch --show-current

main이 출력되어야 합니다. 다르면 병합하지 않습니다.

  1. 이번 한 줄에서는 전환 뒤 상태가 깨끗한지 확인합니다.
git status --short

아무것도 출력되지 않아야 합니다. 파일 이름이 보이면 병합하지 않습니다.

  1. 이번 한 줄에서는 병합 전 두 브랜치의 차이를 확인합니다.
git diff main..feature/add-next-step

새 문장 한 줄이 추가된 차이가 보여야 합니다. 다른 변경이나 오류가 보이면 병합하지 않습니다.

  1. 이번 한 줄에서는 확인한 기능 브랜치를 fast-forward 방식으로만 병합합니다.
git merge --ff-only feature/add-next-step

Fast-forward와 바뀐 파일 정보가 출력되어야 합니다. 오류가 보이면 브랜치를 삭제하지 않습니다.

  1. 이번 한 줄에서는 병합 뒤 상태가 깨끗한지 확인합니다.
git status --short

성공하면 아무것도 출력되지 않습니다. 파일 이름이 보이면 브랜치를 삭제하지 않습니다.

  1. 이번 한 줄에서는 병합 뒤 로그에서 main과 기능 브랜치 위치를 확인합니다.
git log --oneline --decorate --graph --all -4

최신 줄에 HEAD -> main과 feature/add-next-step이 함께 보여야 합니다. 다르면 브랜치를 삭제하지 않습니다.

  1. 이번 한 줄에서는 병합된 문장이 README에 있는지 확인합니다.
cat README.md

마지막에 새 문장이 보여야 합니다. 보이지 않으면 브랜치를 삭제하지 않습니다.

  1. 이번 한 줄에서는 병합을 확인한 기능 브랜치 이름을 정리합니다.
git branch -d feature/add-next-step

삭제했다는 문장이 출력되어야 합니다. 병합되지 않았다는 오류가 보이면 강제 삭제하지 않습니다.

  1. 이번 한 줄에서는 남은 브랜치를 확인합니다.
git branch

별표가 붙은 main만 보여야 합니다. 다른 브랜치가 보이면 완료가 아닙니다.

최신 줄에 (HEAD -> main)과 docs: add next step이 보여야 합니다.
