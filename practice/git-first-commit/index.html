변경을 확인하고 첫 커밋 남기기

Git 01 · 확인한 파일만 스테이징하고 기록하기

GIT 01 · Git과 협업 · 로컬 실습

표준 환경 · macOS · Terminal · zsh · VS Code · Git 2.28+

오늘의 미션

nobase-practice/git-first-commit을 로컬 Git 저장소로 만들고 첫 커밋을 남깁니다. 중요한 것은 git add를 빨리 입력하는 일이 아니라, 작업 폴더의 변경 → 스테이징할 변경 → 실제 커밋을 각각 눈으로 확인하는 일입니다.

시작 상태와 안전선

이 실습은 GitHub 로그인, 원격 저장소, push 없이 내 컴퓨터에서만 진행합니다. CLI 02를 하지 않았어도 괜찮습니다. 아래에서는 명령을 한 줄씩 입력하고, 바로 아래 설명에서 결과를 확인한 뒤 다음 줄로 넘어갑니다.

mkdir는 폴더를 만드는 명령이고, -p는 상위 폴더가 이미 있어도 오류 없이 필요한 폴더만 준비하는 옵션입니다. 이번 한 줄에서는 모든 실습이 함께 사용할 nobase-practice 폴더를 준비합니다.

mkdir -p ~/nobase-practice

성공하면 아무것도 출력되지 않습니다. 오류가 보이면 다음 명령을 입력하지 말고 오류에 나온 경로와 철자를 확인합니다.

cd는 현재 위치를 다른 폴더로 옮기는 명령입니다. 이번 한 줄에서는 방금 준비한 공통 실습 폴더로 이동합니다.

cd ~/nobase-practice

성공하면 아무것도 출력되지 않습니다. no such file or directory가 보이면 다음 명령을 입력하지 말고 앞의 mkdir 명령과 경로를 다시 확인합니다.

ls는 현재 폴더에 있는 이름을 보여 주는 명령입니다. 이번 한 줄에서는 같은 이름의 실습 폴더가 이미 있는지 확인합니다.

ls

기존 파일과 폴더 이름이 출력되거나, 비어 있으면 아무것도 출력되지 않습니다. 여기서 git-first-commit이 보이면 중단합니다. 그 경로로 들어가거나, 지우거나, 파일을 추가하지 말고 강사에게 기존 실습을 어떻게 보관할지 확인합니다.

옵션 없는 mkdir는 같은 이름이 이미 있으면 실패하므로 기존 경로를 바꾸지 않습니다. 이번 한 줄에서는 이 글만 사용할 새 폴더를 만듭니다.

mkdir git-first-commit

성공하면 아무것도 출력되지 않습니다. File exists 같은 오류가 보이면 기존 경로를 사용하지 말고 여기서 중단합니다.

이번 한 줄에서는 새로 만든 이 글의 실습 폴더로 이동합니다.

cd git-first-commit

성공하면 아무것도 출력되지 않습니다. 오류가 보이면 다음 명령을 입력하지 말고 앞의 mkdir 결과와 현재 이름을 확인합니다.

touch는 없는 파일을 빈 파일로 만드는 명령입니다. 이번 한 줄에서는 이 글에서 새로 만든 폴더임을 나타내는 안전 표식 파일을 만듭니다.

touch .nobase-practice-root

성공하면 아무것도 출력되지 않습니다. 오류가 보이면 다음 명령을 입력하지 말고 현재 폴더의 쓰기 권한과 철자를 확인합니다.

pwd는 현재 폴더의 전체 경로를 보여 줍니다. 이번 한 줄에서는 정확한 실습 폴더에 들어왔는지 확인합니다.

pwd

출력 끝이 /nobase-practice/git-first-commit이어야 합니다. 다르면 다음 명령을 입력하지 말고 cd 단계부터 경로를 다시 확인합니다.

ls -la의 -l은 자세한 정보, -a는 점으로 시작하는 숨김 파일까지 보여 주는 옵션입니다. 이번 한 줄에서는 안전 표식이 실제로 생겼는지 확인합니다.

ls -la

목록에 .nobase-practice-root가 보여야 합니다. 보이지 않으면 다음 명령을 입력하지 말고 touch 명령의 철자를 확인합니다.

git --version은 설치된 Git 버전을 보여 줍니다. 이번 한 줄에서는 실습에 필요한 Git 2.28 이상인지 확인합니다.

git --version

git version 2.28.0처럼 버전이 출력됩니다. 2.28보다 낮거나 명령을 찾을 수 없다는 오류가 나오면 저장소를 만들지 말고 Git 설치 상태를 먼저 확인합니다. 이 글은 실제 프로젝트, 전역 Git 설정, 기존 GitHub 자격 증명을 건드리지 않습니다.

처음 만나는 말

  • 저장소(repository): Git이 파일 변경과 기록을 관리하는 프로젝트 폴더입니다.
  • 작업 폴더(working tree): 현재 직접 보고 수정하는 파일 상태입니다.
  • 스테이징 영역(index): 다음 커밋에 넣기로 고른 변경을 잠시 모아 두는 곳입니다.
  • 커밋(commit): 선택한 변경과 설명을 하나의 기록으로 남긴 것입니다.
  • diff: 두 상태 사이에서 무엇이 추가·삭제됐는지 보여 주는 차이입니다.

명령을 직접 입력하기

1. 시작 파일을 만들고 VS Code로 편집하기

이번 한 줄에서는 메모 파일을 담을 notes 폴더를 만듭니다.

mkdir notes

성공하면 아무것도 출력되지 않습니다. 오류가 보이면 다음 명령을 입력하지 말고 pwd와 ls -la로 현재 위치와 기존 이름을 확인합니다.

이번 한 줄에서는 README, 오늘의 메모, Git 제외 규칙 파일을 빈 파일로 만듭니다.

touch README.md notes/today.txt .gitignore

성공하면 아무것도 출력되지 않습니다. 오류가 보이면 다음 명령을 입력하지 말고 ls -la와 ls notes로 만들어진 이름을 확인합니다.

macOS의 open -a는 지정한 앱으로 파일을 여는 명령입니다. 이번 한 줄에서는 세 파일을 Visual Studio Code로 엽니다.

open -a "Visual Studio Code" README.md notes/today.txt .gitignore

터미널에는 보통 아무것도 출력되지 않고 VS Code 창이나 탭이 열립니다. 앱을 찾을 수 없다는 오류가 보이면 파일 내용을 입력하지 말고 VS Code의 설치 이름을 확인합니다.

VS Code에서 각 파일에 다음 내용을 입력하고 저장합니다.

README.md:

# Practice Project
CLI와 Git 상태 확인을 연습합니다.

notes/today.txt:

명령 뒤에는 상태를 확인한다.

.gitignore:

.DS_Store
.env
.nobase-practice-root

cp는 원본을 새 이름으로 복사합니다. 이번 한 줄에서는 오늘의 메모를 archive.txt로 복사합니다.

cp notes/today.txt notes/archive.txt

성공하면 아무것도 출력되지 않습니다. 오류가 보이면 다음 명령을 입력하지 말고 ls notes에서 원본 이름을 확인합니다.

cat은 파일 내용을 터미널에 보여 줍니다. 이번 한 줄에서는 Git에서 제외할 이름을 확인합니다.

cat .gitignore

.DS_Store, .env, .nobase-practice-root가 한 줄씩 보여야 합니다. 다르면 다음 명령을 입력하지 말고 VS Code에서 .gitignore를 고쳐 저장합니다.

이번 한 줄에서는 README에 저장한 두 줄을 확인합니다.

cat README.md

# Practice Project와 설명 문장이 보여야 합니다. 다르면 다음 명령을 입력하지 말고 README를 고쳐 저장합니다.

이번 한 줄에서는 오늘의 메모 내용을 확인합니다.

cat notes/today.txt

명령 뒤에는 상태를 확인한다.가 보여야 합니다. 다르면 다음 명령을 입력하지 말고 파일을 고쳐 저장합니다.

이번 한 줄에서는 복사본의 내용도 원본과 같은지 확인합니다.

cat notes/archive.txt

원본과 같은 문장이 보여야 합니다. 다르면 다음 명령을 입력하지 말고 cp에 입력한 두 경로를 확인합니다. archive.txt까지 만드는 이유는 CLI 02를 먼저 했을 때와 하지 않았을 때 모두 같은 Git 시작 상태를 만들기 위해서입니다.

2. main 브랜치로 저장소 시작하기

git init은 현재 폴더를 Git 저장소로 만들고, -b main은 첫 브랜치 이름을 main으로 정합니다. 이번 한 줄에서는 현재 실습 폴더에서 저장소를 시작합니다.

git init -b main

초기화했다는 문장과 현재 경로가 출력됩니다. 오류가 보이면 다음 명령을 입력하지 말고 pwd, ls -la, git --version을 차례로 다시 확인합니다.

git config --local은 설정을 현재 저장소에만 기록합니다. 이번 한 줄에서는 연습 커밋에 표시할 이름을 로컬 설정으로 저장합니다.

git config --local user.name "Practice Learner"

성공하면 아무것도 출력되지 않습니다. 오류가 보이면 다음 명령을 입력하지 말고 현재 폴더에 .git이 있는지 ls -la로 확인합니다.

이번 한 줄에서는 실제 주소가 아닌 연습용 이메일을 현재 저장소에만 저장합니다.

git config --local user.email "practice@example.invalid"

성공하면 아무것도 출력되지 않습니다. example.invalid는 실제 메일 전송에 사용되지 않는 연습용 도메인입니다. 오류가 보이면 커밋 단계로 넘어가지 말고 로컬 저장소 초기화 상태를 확인합니다.

이번 한 줄에서는 저장된 로컬 사용자 이름을 확인합니다.

git config --local user.name

Practice Learner가 출력되어야 합니다. 다르면 다음 명령을 입력하지 말고 앞의 이름 설정 명령을 다시 확인합니다.

이번 한 줄에서는 저장된 로컬 연습 이메일을 확인합니다.

git config --local user.email

practice@example.invalid가 출력되어야 합니다. 다르면 다음 명령을 입력하지 말고 앞의 이메일 설정 명령을 다시 확인합니다.

3. add 전에 변경 내용 확인하기

git status --short의 --short는 현재 변경을 짧은 기호로 보여 줍니다. 이번 한 줄에서는 스테이징하기 전 파일 목록을 확인합니다.

git status --short

.gitignore, README.md, notes/ 앞에 ??가 보일 수 있습니다. ??는 Git이 아직 추적하지 않는다는 뜻입니다. 안전 표식과 .env는 .gitignore 규칙 때문에 보이지 않아야 합니다. 예상하지 못한 파일이 보이면 git add를 입력하지 말고 파일 이름과 내용을 먼저 확인합니다.

git diff는 작업 폴더와 스테이징 영역의 차이를 보여 줍니다. 이번 한 줄에서는 아직 스테이징하지 않은 변경을 확인합니다.

git diff

새 파일은 아직 Git이 추적하지 않으므로 지금은 아무것도 출력되지 않을 수 있습니다. 이 빈 출력은 오류가 아닙니다. 오류가 보이면 git add를 입력하지 말고 앞의 git status --short 결과를 확인합니다.

git diff --staged의 --staged는 다음 커밋에 들어가도록 고른 변경만 보여 줍니다. 이번 한 줄에서는 스테이징 영역이 아직 비어 있는지 확인합니다.

git diff --staged

아직 아무것도 고르지 않았으므로 성공하면 아무것도 출력되지 않습니다. 내용이 보이면 git add를 입력하지 말고 이미 스테이징된 파일 이름을 확인합니다.

이번 한 줄에서는 제외 규칙에 민감한 파일 이름이 없는지 다시 읽습니다.

cat .gitignore

세 줄의 보호 규칙이 그대로 출력되어야 합니다. .env 또는 안전 표식 규칙이 빠졌다면 git add를 입력하지 말고 파일을 고쳐 저장합니다.

이번 한 줄에서는 커밋할 README 내용을 다시 읽습니다.

cat README.md

앞에서 저장한 두 줄만 보여야 합니다. 실제 이메일, 키, 비밀번호 같은 정보가 보이면 git add를 입력하지 말고 제거합니다.

이번 한 줄에서는 커밋할 오늘의 메모를 다시 읽습니다.

cat notes/today.txt

연습 문장 한 줄만 보여야 합니다. 예상하지 못한 내용이 보이면 git add를 입력하지 말고 파일을 고칩니다.

이번 한 줄에서는 커밋할 메모 복사본을 다시 읽습니다.

cat notes/archive.txt

오늘의 메모와 같은 한 줄만 보여야 합니다. 다르면 git add를 입력하지 말고 복사 과정을 확인합니다.

4. 파일을 나누어 스테이징하기

git add는 다음 커밋에 넣을 파일을 스테이징 영역에 고릅니다. 이번 한 줄에서는 제외 규칙과 README만 먼저 고릅니다.

git add .gitignore README.md

성공하면 아무것도 출력되지 않습니다. 오류가 보이면 다음 명령을 입력하지 말고 오류에 나온 파일 이름과 ls -la 결과를 확인합니다.

이번 한 줄에서는 첫 번째 git add 뒤의 상태를 확인합니다.

git status --short

.gitignore와 README.md 앞에는 A , 아직 고르지 않은 notes/ 앞에는 ??가 보여야 합니다. 다르면 다음 git add를 입력하지 말고 파일 이름을 확인합니다.

이번 한 줄에서는 지금까지 스테이징한 두 파일의 실제 내용을 확인합니다.

git diff --staged

.gitignore와 README.md의 추가 내용만 보여야 합니다. 다른 파일이 보이면 다음 git add를 입력하지 말고 현재 스테이징 목록을 점검합니다.

이번 한 줄에서는 두 메모 파일을 다음 커밋에 추가로 고릅니다.

git add notes/today.txt notes/archive.txt

성공하면 아무것도 출력되지 않습니다. 오류가 보이면 커밋하지 말고 ls notes로 실제 파일 이름을 확인합니다.

이번 한 줄에서는 두 번째 git add 뒤 모든 대상이 준비됐는지 확인합니다.

git status --short

네 파일 모두 앞에 A 가 보여야 하고 ??는 남지 않아야 합니다. 다르면 커밋하지 말고 빠졌거나 예상하지 못한 파일 이름을 확인합니다.

이번 한 줄에서는 첫 커밋에 들어갈 네 파일의 최종 차이를 확인합니다.

git diff --staged

파일 목록과 내용이 .gitignore, README.md, 두 메모 파일과 일치해야 합니다. .env, 안전 표식, 실제 이메일, 키 같은 내용이 보이면 커밋하지 말고 원인을 먼저 확인합니다.

5. 첫 커밋 만들기

git commit -m의 -m은 커밋 설명을 명령 안에 적는 옵션입니다. 이번 한 줄에서는 스테이징한 네 파일을 첫 기록으로 남깁니다.

git commit -m "docs: add practice project files"

성공하면 커밋 식별자, 메시지, 변경된 파일 수가 출력됩니다. 오류가 보이면 다음 명령을 입력하지 말고 오류 문장과 git status --short 결과를 확인합니다.

이번 한 줄에서는 커밋 뒤 작업 폴더에 남은 변경이 없는지 확인합니다.

git status --short

성공했고 모든 변경을 커밋했다면 아무것도 출력되지 않습니다. 이 빈 출력이 깨끗한 상태라는 뜻입니다. 파일 이름이 보이면 로그를 확인하기 전에 어떤 변경이 남았는지 살펴봅니다.

git log --oneline --decorate -1은 최근 기록 한 개를 짧게 보여 주고 현재 브랜치 표시도 붙입니다. 이번 한 줄에서는 첫 커밋이 main에 남았는지 확인합니다.

git log --oneline --decorate -1

컴퓨터마다 다른 짧은 해시와 함께 (HEAD -> main) 및 docs: add practice project files가 보여야 합니다. 다르면 다음 단계로 가지 말고 현재 브랜치와 커밋 메시지를 확인합니다.

출력에서 확인할 것

  1. 첫 status의 ??가 git add 뒤 A 로 바뀌었는가?
  2. 일반 git diff와 git diff --staged가 보는 대상이 어떻게 달랐는가?
  3. 커밋 뒤 status --short가 비어 있는가?
  4. git log에서 현재 브랜치와 커밋 메시지를 찾을 수 있는가?

정상 흐름 완료

이번 한 줄에서는 마지막 현재 경로를 확인합니다.

pwd

출력 끝이 /nobase-practice/git-first-commit이어야 합니다. 다르면 다른 명령을 입력하지 말고 실습 폴더로 돌아갑니다.

이번 한 줄에서는 안전 표식과 저장소 폴더를 함께 확인합니다.

ls -la

.nobase-practice-root와 .git이 모두 보여야 합니다. 하나라도 없으면 완료로 판정하지 말고 시작 단계와 저장소 초기화 단계를 확인합니다.

git branch --show-current는 현재 브랜치 이름만 보여 줍니다. 이번 한 줄에서는 현재 브랜치가 main인지 확인합니다.

git branch --show-current

main이 출력되어야 합니다. 다른 이름이 보이면 완료로 판정하지 말고 현재 브랜치를 확인합니다.

이번 한 줄에서는 마지막 Git 상태가 깨끗한지 확인합니다.

git status --short

아무것도 출력되지 않아야 합니다. 파일 이름이 보이면 완료로 판정하지 말고 남은 변경을 확인합니다.

이번 한 줄에서는 마지막 커밋 한 개와 현재 브랜치를 확인합니다.

git log --oneline --decorate -1

(HEAD -> main)과 첫 커밋 메시지가 한 줄에 보여야 합니다. 다르면 완료로 판정하지 않습니다.

대표 실패와 복구

git add 뒤에 존재하지 않는 이름을 주면 Git이 오류를 보여 주고 기존 커밋은 바꾸지 않습니다. 이번 한 줄에서는 일부러 없는 파일 이름을 입력해 오류를 읽습니다.

git add file-that-does-not-exist.txt

pathspec과 파일이 일치하지 않는다는 오류가 보입니다. 오류 뒤에는 다른 파일을 추측해 입력하지 말고, 다음 확인 명령으로 현재 상태를 먼저 읽습니다.

이번 한 줄에서는 실패 뒤 Git 상태가 바뀌지 않았는지 확인합니다.

git status --short

기존 상태가 깨끗하므로 아무것도 출력되지 않아야 합니다. 파일 이름이 보이면 다음 명령을 입력하지 말고 그 변경부터 확인합니다.

이번 한 줄에서는 현재 폴더의 실제 파일 이름을 확인합니다.

ls

README.md와 notes가 보이고, 존재하지 않는 파일 이름은 보이지 않습니다. 이 실패만으로 이미 만든 커밋은 바뀌지 않습니다.

완료 확인

README에 새 줄을 추가하면 어떤 상태가 보일지 먼저 예측합니다.

이번 한 줄에서는 README를 VS Code로 엽니다.

open -a "Visual Studio Code" README.md

터미널에는 보통 아무것도 출력되지 않고 README 탭이 열립니다. 오류가 보이면 파일을 수정하지 말고 앱 이름과 ls의 파일 이름을 확인합니다.

파일 끝에 다음 한 줄을 추가하고 저장합니다.

작은 변경은 확인한 뒤 기록한다.

이번 한 줄에서는 저장 뒤 README가 어떤 Git 상태인지 확인합니다.

git status --short

README.md 앞에 M이 보여야 합니다. 보이지 않으면 다음 명령을 입력하지 말고 VS Code에서 저장했는지 확인합니다.

이번 한 줄에서는 아직 스테이징하지 않은 새 문장을 확인합니다.

git diff

추가한 문장 앞에 +가 붙어 보여야 합니다. 예상하지 못한 다른 변경이 보이면 변형 과제를 진행하지 말고 README 내용을 확인합니다.

출력에서 README.md가 아직 스테이징되지 않은 변경임을 설명합니다.

힌트 없는 변형 과제: 이 새 줄만 두 번째 커밋으로 남기세요. 커밋 전에는 스테이징된 diff를, 커밋 뒤에는 빈 status와 두 줄의 log를 증거로 보여 주세요.

변형 과제 정답 확인하기
  1. 이번 한 줄에서는 변경한 README만 스테이징합니다.
git add README.md

성공하면 아무것도 출력되지 않습니다. 오류가 보이면 다음 단계로 가지 말고 README 이름과 현재 위치를 확인합니다.

  1. 이번 한 줄에서는 README가 스테이징됐는지 확인합니다.
git status --short

README.md 앞에 M 이 보여야 합니다. 다르면 커밋하지 말고 상태를 다시 읽습니다.

  1. 이번 한 줄에서는 두 번째 커밋에 들어갈 실제 차이를 확인합니다.
git diff --staged

방금 추가한 한 줄만 보여야 합니다. 다른 변경이 보이면 커밋하지 않습니다.

  1. 이번 한 줄에서는 확인한 README 변경을 두 번째 커밋으로 남깁니다.
git commit -m "docs: add small change rule"

성공하면 새 커밋 식별자와 메시지가 출력됩니다. 오류가 보이면 다음 단계로 가지 말고 오류 문장과 상태를 확인합니다.

  1. 이번 한 줄에서는 커밋 뒤 남은 변경이 없는지 확인합니다.
git status --short

성공하면 아무것도 출력되지 않습니다. 파일 이름이 보이면 완료가 아닙니다.

  1. 이번 한 줄에서는 최근 커밋 두 개를 확인합니다.
git log --oneline --decorate -2

두 번째 커밋과 첫 커밋이 차례로 보이고 최신 줄에는 (HEAD -> main)이 표시되어야 합니다.
